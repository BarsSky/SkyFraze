# Импорт и экспорт папкой: md, zip и правила формата

Заметка о том, как организовать «выгрузить проект в md / zip с ассетами» и «загрузить
папку, где по подкаталогам лежат md». Написана по факту текущего кода: перенос проектов
уже есть (`backend/internal/transfer/`, кнопки на странице проектов), текст события —
Markdown (0.5.0), поэтому обе задачи — это сборка и разбор дерева, а не конвертация
формата.

**Что из этого уже сделано** (ниже по тексту пункты помечены): выгрузка одной лентой и
zip с ассетами (0.14.0), импорт папки с предпросмотром (0.14.0), вложения при импорте —
картинки становятся вложениями событий и фоном кадра (0.16.0), импорт «в место» в
существующий проект (0.15.0), квота проекта, которая распространяется и на импорт
(0.21.0), вес набора в предпросмотре (0.24.0). Правила формата (§3) — действующие, а не
планы: по ним работает `TestMarkdownRoundTrip` на бэкенде. Разделы, где текст расходился
с кодом, приведены к тому, что есть на самом деле; версия формата переноса осталась
**1** (её поднимать не понадобилось: `story.md` и `story/` добавляются внутрь архива и
старым импортом просто игнорируются, см. `docs/import-export.md`).

## 1. Что уже есть и что берём готовым

| Что | Где | Чем полезно |
| --- | --- | --- |
| Архив проекта `project.skyfraze.zip` | `backend/internal/transfer/service.go` | обход дерева, стриминг в zip, скачивание с человеческим именем (`SlugifyFileName`) |
| Манифест `manifest.json` | `transfer/service.go:59-95` | полная точность: события (`id`, `parent_id`, `position`, `depth`, `title`, `body`, `event_date`), ассеты (`id`, `filename`, `mime`, `size`, `kind`, размеры, `file`), `has_state` для CRDT-снапшота |
| Проверки архива | `transfer/service.go:258-306` | формат (`skyfraze-project`), версия, потолок размера (`MaxBundleSize = 200 MB`), потолок распакованного (`×4`) |
| UI | `frontend/src/pages/ProjectsPage.tsx` | «Экспорт» у проекта, «Импорт проекта» (архив с другого стенда) |
| Markdown в тексте | `frontend/src/lib/markdown.ts` | тело события уже md: заголовки, списки, таблицы, формулы, диаграммы |

Вывод: новый функционал — это надстройка над `transfer`, а не второй формат.

## 2. Организация «одна коробка — три читателя»

Один zip, внутри которого каждый находит своё:

```
skyfraze.json        манифест (как manifest.json сейчас) — полная точность и версия формата
story.md             ВЕСЬ проект одной лентой: люди, ИИ, pandoc → PDF/EPUB
story/               по файлу на кадр — правка в git и обратный импорт
  01-пролог.md
  01.1-сборка-на-верфи.md
  01.1.1-испытания-корпуса.md
  01.2-старт-с-орбиты.md
assets/              файлы вложений (как сейчас) — на них ссылается и story.md
README.txt           правила формата в двух абзацах
```

Почему так:

- `story.md` — то, что просили: «объединить отображаемый проект в единый md». Ссылки на
  картинки внутри — относительные (`./assets/01-пролог.png`), поэтому распакованная папка
  открывается и рендерится где угодно, включая редакторы и конвертеры.
- `story/*.md` — обратимость. Номера кадров (`01`, `01.1`, `01.1.1`) уже отражают дерево,
  поэтому папка восстанавливается в проект **без манифеста**. Манифест добавляет точность
  (даты, фон, id, порядок вложений), без него — только то, что выражается в md.
- `assets/` остаётся плоским, как сейчас, — совместимость с уже сданными архивами и
  с текущим импортом переноса.
- Старый сценарий «перенести проект на другой стенд» не меняется: `manifest.json` +
  `assets/` — это ровно тот же архив, просто с новыми папками внутри. Версию формата
  поднимать не пришлось: неизвестные файлы (`story.md`, `story/`, `README.txt`) импорт
  переноса просто игнорирует, а `version > 1` по-прежнему отклоняется.

Режимы в UI (на странице проектов, рядом с нынешним «Экспорт») — **сделано**:

1. **«Скачать md»** — только `story.md` (одна лента, без картинок).
2. **«Скачать md + ассеты»** — zip: `story.md` + `assets/` + `README.txt` (то, что просили).
3. **«Полный архив SkyFraze»** — как сейчас (+ `story/`), для переноса между стендами.

## 3. Правила формата (детерминированные, чтобы импорт был предсказуем) — **действующие**

- **Номер кадра** — префикс имени файла: `01`, `01.1`, `01.1.1`, картинка `01.1·1`.
  В `story.md` тот же номер печатается как подпись/подзаголовок, поэтому лента
  сопоставляется с папкой однозначно.
- **Заголовок**: front-matter `title:` → иначе первый `# H1` в файле → иначе имя файла без
  номера (дефисы → пробелы). Заголовок никогда не берётся из имени «навсегда»: в
  front-matter он сохраняется точно (регистр, кавычки, пунктуация).
- **Вложенность**: каталог = уровень (`03-глава/01-под-событие.md`), а `index.md` внутри
  каталога — это само событие каталога (тогда картинки события лежат рядом с ним).
- **Front-matter** (необязательный YAML): `title`, `date`, `bg` (`tone:#8FB98A` или
  `asset: картинка.png`), `position`. Нет front-matter — импорт всё равно работает по
  номерам и заголовкам.
- **Порядок**: числовой префикс, затем имя файла. Файлы без номера — в конец, с
  предупреждением.
- **Кодировка**: UTF-8 (BOM допускается), CRLF нормализуется, пустые файлы дают пустое
  событие и предупреждение. Всё, что не `.md`/`.markdown`, вложениями становится только
  по ссылке из текста — см. `docs/import-export.md` § 2.5 (картинка, на которую никто не
  ссылается, в проект не попадает, и об этом сообщают).
- **Что теряется без манифеста**: id, время даты, настройки фона, порядок и подписи
  вложений. Импорт обязан собрать это в отчёт («не перенесено: 3 настройки фона, 12
  ссылок на изображения»), а не молча потерять.

## 4. Импорт папки с md — **сделано** (вложения — с 0.16.0)

Поток:

1. Пользователь тащит папку (или выбирает через `input type="file" webkitdirectory`) —
   на телефоне вместо папки принимаем zip.
2. Сервер разбирает файлы, строит дерево и **ничего не пишет**: возвращает предпросмотр —
   список глав и под-событий, номера, сколько знаков в каждом, вес вложений и предел
   проекта, предупреждения (пустые файлы, глубина больше 4, ненайденные ссылки, файлы без
   ссылок, настройка фона, дата не в формате).
3. Пользователь подтверждает → создаётся **новый проект**: события, вложения и
   CRDT-снапшот с привязками файлов (иначе картинки пришлось бы прикреплять заново).
4. Вложения приезжают в проект: картинки пережимаются в WebP, ссылки в текстах
   заменяются на адреса вложений, первая картинка события становится фоном кадра. Импорт
   подчиняется квоте проекта: набор, который не помещается, отклоняется целиком и за собой
   ничего не оставляет.

Отдельно есть **импорт «в место»** — тот же набор вставляется в существующий проект
(`docs/import-export.md` § 2.4): проверка глубины до записи, вставка в документ живой
комнаты, повторный импорт того же куска задваивает его (идемпотентности нет — повтор
запрещает сама проверка глубины только там, где кусок не влезает).

Почему предпросмотр обязателен: правила (номера, каталоги, front-matter) должен видеть
человек до записи в проект, иначе любая неожиданность в именах файлов превращается в
кривое дерево, которое потом руками разбирать.

## 5. Что понадобится учесть (главное) — состояние на сейчас

1. **Два источника правды: CRDT и таблица событий.** — **решено.** Импорт в новый проект
   пишет и строки `events`, и CRDT-снапшот с привязками вложений и фоном (0.16.0); импорт
   «в место» идёт в документ живой комнаты, а таблица событий перестраивается из него
   (0.15.0). Запись мимо комнаты по-прежнему запрещена: её затёрло бы ближайшее сохранение.
2. **Безопасность архива** — **сделано**, и больше, чем планировалось: пути нормализуются
   (`cleanInputPath`), отвергаются абсолютные пути (`/…`, `C:/…`), `..` в любом сегменте,
   управляющие символы и NUL; симлинки в zip отвергаются по режиму записи; лимиты — 2000
   файлов, 4 МБ на md-файл, 50 МБ на вложение, 200 МБ на суммарный распакованный объём
   (`c.total` считает и md, и вложения) и 200 МБ на сам архив; размер записи проверяется по
   заголовку zip — до распаковки, а чтение идёт через `readLimited`, поэтому лживый
   заголовок не раздувает память. Коэффициент распаковки отдельной проверкой не считаем:
   суммарный потолок и потолок на файл закрывают тот же риск.
3. **Имена и слаги** — **сделано**: имя файла для скачивания — слаг (`SlugifyFileName`),
   заголовок хранится отдельно и точно.
4. **Дубли и пробелы** — **сделано частично, осознанно**: пустой файл, глубина больше 4,
   ненайденная ссылка, файл без ссылок, `bg` и дата не в формате — это предупреждения, а
   разбор продолжается. Два файла с одним номером не отвергаются: номер — не ключ, порядок
   задаётся префиксом и именем, а совпадение номеров видно в предпросмотре глазами.
5. **Транзакционность и повтор** — **сделано в другой форме**: импорт создаёт новый проект
   и при любой ошибке убирает за собой (строки вложений и файлы); повторная загрузка той же
   папки создаст второй проект — это и есть ожидаемое поведение, «заменить» не нужно.
   Импорт «в место» повтор задваивает: он вставляет кусок, а не синхронизирует папку.
6. **Права** — **сделано**: экспорт — `viewer+` (читатель и так видит содержимое), импорт в
   новый проект — любому вошедшему, импорт «в место» — `editor+`.
7. **Транспорт** — **решено иначе**: потолок остался 200 МБ, а папка с картинками больше
   него не «поднимается» — её принимают по частям или через zip (потолок распаковки тот же).
8. **Производительность** — **сделано**: экспорт стримится в zip, импорт читает набор
   потоково (zip — по одной записи), но разобранные файлы держатся в памяти: это и есть
   причина потолка 200 МБ.
9. **Договор с внешними инструментами** — **сделано на бэкенде**: правила формата описаны в
   `docs/import-export.md`, обратимость проверяет `TestMarkdownRoundTrip` (экспорт → импорт →
   сравнение дерева, вложений и дат). Отдельного e2e-сценария в браузере нет: браузерная
   часть (выбор папки, предпросмотр) проверяется тестами компонентов, а перенос — на Go.

Отдельно стоит держать в голове: `story.md` уже есть, поэтому почти бесплатно получаются

с другим оформлением. Пока этого нет: сегодня выгрузка отдаёт всю историю целиком.
