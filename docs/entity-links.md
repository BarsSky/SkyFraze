# Связи внутри проекта: персонажи, места, темы

Разбор идеи «связать кадры через общие сущности», с решением и планом. Документ-разбор, как
`docs/webauthn.md` и `docs/fragment-comments.md`: сначала почему так, потом что делать.

## 1. Что просят и что для этого уже есть

Задача: не терять взаимосвязь внутри проекта — видеть, какие кадры связаны одним персонажем,
местом или темой, и видеть это как хронологию, а не как список совпадений слов.

Что уже лежит в проекте и на что можно опереться:

| Что есть | Где | Чем полезно |
|---|---|---|
| Весь текст проекта в CRDT на клиенте | `frontend/src/collab/` (`eventTree`, `liveText`), `backend/internal/collab/yjs` | распознавание упоминаний можно делать мгновенно, без запроса к серверу — как работает поиск по дереву |
| Якоря фрагментов (`Y.RelativePosition`) | `backend/internal/collab/yjs/anchor.go`, `frontend/src/collab/anchors.ts`, миграция `0026` | ссылка на место в тексте переживает правки; это уже проверенный механизм (замечания к фрагментам, 0.60.0) |
| Переход к фрагменту и подсветка диапазона | `EventEditor` (`focusRange`), 0.63.0 | «показать в тексте» уже умеет выделять диапазон в поле кадра |
| Проекция дерева в Postgres | `events`, `project_event_state` (0002), `internal/collab/hub.go` | тот же путь для серверных выборок: CRDT — источник, таблицы — отражение |
| Разбор упоминаний по нику | `backend/internal/events/comments.go` (`ParseMentions`) | прецедент: правила разбора и проверка уже написаны для `@ник` |
| Дата кадра | `event_date` в CRDT и проекции | по ней строится настоящая хронология, а не порядок в дереве |

Чего нет: ни персонажей, ни мест, ни тем как объектов. Сейчас кадр — это `id`, `parent_id`,
заголовок, текст, дата и фон.

## 2. Почему одни теги не подойдут — и в чём идея верна

Идея «теги + связи из упоминаний» верна во второй половине: **источник связи — упоминание в
тексте**, а не ручное приклеивание метки к кадру. Ручное протухает: кадр переписали, метка
осталась.

Но **сами теги как хранилище — плохой выбор для персонажей**:

| Ситуация | Что происходит с тегом | Что происходит с карточкой и алиасами |
|---|---|---|
| «Анна», «Анны», «Анне» | три разных тега или ни одного совпадения | один персонаж, алиасы: `Анна`, `Анны`, `Анне` |
| «Аня» в диалоге, «Анна Сергеевна» в официальной сцене | не находит | алиасы `Аня`, `Анна Сергеевна` |
| «дом» (место) и «дом» (жилище вообще) | склеиваются молча | алиас можно не заводить — не всякое слово это место |
| Нужно «где на таймлайне появляется Анна» | невозможно: тег без идентичности | обычный запрос по `entity_id` |
| Нужно краткое описание («кто это») | негде | у карточки есть описание, и его читают соавторы |

Поэтому: **карточка сущности (персонаж / место / тема) с именем, алиасами и описанием** —
это и есть «тег», только с идентичностью. Тег остаётся способом быстро пометить кадр вручную
(«без диалогов»), но связь «персонаж ↔ кадры» ведётся по карточке.

## 3. Решение

### 3.1. Данные

**В CRDT-документе проекта** — новая корневая карта `entities` (по образцу `events`):

```
entities: {
  "<uuid>": {
    kind: "character" | "place" | "theme",
    name: "Анна",
    aliases: ["Аня", "Анны", "Анне"],   // Y.Array строк
    description: "…",                    // Y.Text, правится совместно
    color: "#c9a227",                    // для подсветки в тексте
    created_by, created_at
  }
}
```

Почему в CRDT, а не только в Postgres: карточка — часть проекта, как кадр. Тогда совместная
правка, история версий (`project_revisions`), экспорт/импорт архива и удаление проекта работают
без отдельной синхронизации. Это же правило проекта: источник — документ, таблицы — отражение.

**В Postgres** — две таблицы (миграция `0030`):

```sql
project_entities (
  id uuid PK, project_id uuid FK, kind text, name text,
  aliases text[], description text, color text, deleted_at timestamptz?
);
event_entity_mentions (
  id uuid PK,
  project_id uuid FK, event_id uuid FK, entity_id uuid FK,
  field text CHECK (field IN ('body','title')),
  start_relpos bytea, end_relpos bytea,   -- те же якоря, что у замечаний (0026)
  quote text,                             -- что было в момент связи
  UNIQUE (event_id, entity_id, field, start_relpos)
);
```

`event_entity_mentions` — не «истина», а индексируемое отражение для списков и фильтров:
«кадры с Анной», «персонажи в кадре», «сироты». Якорь нужен, чтобы:
* подсветить точное место в тексте (`focusRange` уже есть);
* заметить, что текст на этом месте изменился: цитата не совпадает → связь «повреждена», её
  видно и её можно перепривязать (как замечания к фрагменту, 0.60.0: `quote` + проверка).

### 3.2. Как находятся упоминания

Правила (те же принципы, что у `ParseMentions`, но строже к падежам):

1. Ищем по алиасам, **самый длинный первым** («Анна Сергеевна» раньше «Анна»), чтобы не
   получать две связи на одном месте.
2. **Границы слова** по Unicode-буквам, а не `\b`: «Анна» не должна находиться в «Аннами».
   Алиас хранится в той форме, в какой его видит текст; падежи — это отдельные алиасы (никакой
   морфологии: словарь падежей русского языка — не наша задача и источник неверных связей).
3. **Одно место — одна связь**: пересечения диапазонов отбрасываются по приоритету
   (длиннее → раньше добавленный алиас).
4. **Ручная правка сильнее автоматики**: у связи есть отметка `manual` / `auto`. «Это не Анна»
   отключает упоминание и не даёт ему вернуться при пересчёте; «Анна здесь без имени» —
   добавляет связь вручную (без диапазона, только «участвует в кадре»).
5. Пересчёт — на клиенте при правке текста (дебаунс), результат уезжает на сервер тем же
   путём, что проекция дерева.

### 3.3. Что видит человек

Пять элементов, каждый отвечает на свой вопрос:

| Где | Что | Вопрос, на который отвечает |
|---|---|---|
| Панель «Связи» (список) | карточки персонажей/мест/тем с числом кадров, поиск по имени | «кто вообще есть в проекте» |
| Карточка сущности | хронология: кадры по `event_date`, при отсутствии — по порядку в дереве; клик → кадр и подсветка упоминания | «где и когда появляется Анна» |
| Кадр | «участники»: сущности, упомянутые в заголовке и тексте | «кто и что в этой сцене» |
| Дерево | фильтр/подсветка «только кадры с сущностью» | «показать линию персонажа по структуре» |
| «Сироты» | сущности без кадров; кадры без сущностей | **«что я теряю»** — ровно исходная задача |

Отдельно (фаза 3) — **матрица связей**: строки персонажи, столбцы главы/кадры, точки —
появления. Это и есть «общий таймлайн»: видно, кто пересекается в одной сцене, а кто ни разу.

## 4. Чего сознательно не делаем

* **Автоматических связей без подтверждения и без показа**: связь всегда видна в тексте
  (подсветка) и её можно снять. Иначе появляется «умный» список, которому не доверяют.
* **Глобальных сущностей между проектами** (общий мир на несколько книг): это отдельный
  контур — идентификаторы, права, миграция. Пока карточки живут внутри проекта; при экспорте
  архива они едут вместе с ним.
* **Морфологии и лемматизации**: падежи — алиасами. Русская морфология в этом месте даёт
  ложные связи и требует словаря, который мы не хотим поддерживать.
* **Связей, которые правит ИИ-помощник**: у помощника уже есть `read_comments` и правки
  фрагментов; давать ему ещё и структуру проекта — отдельный разговор после того, как ручной
  контур проверен.

## 5. Риски и как их проверяем

| Риск | Проверка |
|---|---|
| Ложные срабатывания («дом» как место) | тест: алиас не заводится автоматически; «дом» без карточки не связывается ни с чем |
| Связь «съезжает» при правке текста | тест на якорях: вставка текста до упоминания сохраняет связь; перезапись кадра целиком — помечает связь повреждённой (как замечания) |
| Пересчёт на каждом нажатии клавиши тормозит | замер: 100 кадров × 2000 знаков, 30 карточек — пересчёт за один кадр < 16 мс (дебаунс 300 мс) |
| Дубли в хронологии | уникальность `(event_id, entity_id, field, start)` в БД и правило «одно место — одна связь» |
| Молчаливая потеря связей при импорте | импорт архива переносит карточки и упоминания; e2e: экспорт → импорт → связи на месте |

## 6. План по фазам

| Фаза | Что | Оценка |
|---|---|---|
| 1 | карточки в CRDT (`entities`), миграция `0030`, проекция на сервер, ручки `GET/POST/PATCH/DELETE /api/projects/{id}/entities`, панель «Связи» с созданием и алиасами | 2–3 ч |
| 2 | распознавание упоминаний на клиенте (правила §3.2), «участники кадра», подсветка в тексте, переход к упоминанию | 3–4 ч |
| 3 | хронология сущности, фильтр дерева, «сироты», матрица связей, сохранение упоминаний на сервере | 2–3 ч |
| 4 | e2e (создать персонажа → упомянуть → увидеть в хронологии → экспорт/импорт), визуальная проверка, документация | 1–2 ч |

Итого **8–12 часов**, 2–3 сессии. После фазы 2 уже видно пользу; фазы 3–4 доводят до
«не терять взаимосвязь», а не «есть список персонажей».

## 7. Что решаем сейчас

1. **Карточки с алиасами вместо чистых тегов** (тег остаётся, но как ручная пометка).
2. **Связи из упоминаний в тексте, подтверждённые видимой подсветкой, с ручной правкой.**
3. **Сущности живут внутри проекта** (не общий мир на несколько книг) — первая версия.
4. **Хронология по `event_date`**, при её отсутствии — по порядку дерева (иначе «хронология»
   без дат была бы просто структурой, а это уже есть в дереве).

Если эти четыре пункта устраивают — начинаю с фазы 1 (карточки, проекция, панель), и уже
после неё видно, какие места текста связываются, а какие требуют алиасов.
