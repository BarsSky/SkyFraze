# S3/MinIO для вложений: что это даёт, что ломает и сколько стоит

План, а не отчёт. Правило проекта то же, что и в `docs/storage-compression.md`:
**сначала измерение, потом решение**. Здесь сначала собрано то, что есть сейчас (с
числами по рабочему стенду), потом честно перечислено, что даёт объектное хранилище, чего
оно **не** даёт, что именно ломает в текущем коде и сколько это стоит. В конце — порог,
после которого браться, и что делать вместо, если порог не достигнут.

Короткий вывод, если читать только один абзац: **сейчас не делать.** Объектное хранилище
не экономит место (те же байты), а текущий стенд занимает 6.5 МБ файлов и 10.4 МБ базы;
при этом главная дыра не в хранилище, а в том, что **резервных копий нет вообще**, и MinIO
на том же диске эту дыру не закрывает. Порядок работ поэтому такой: сначала копии (0.5–1
день), потом — если появится вторая площадка, несколько инстансов приложения или объём,
который неудобно копировать, — S3/MinIO (3–5 дней).

## 1. Что есть сейчас (измерено, не «на глаз»)

| Что | Рабочий стенд | Локальный стенд |
| --- | --- | --- |
| База | 10.4 МБ | 12.5 МБ |
| Вложения (строки `assets`) | 5.48 МБ, 4 строки | 4.7 МБ, 22 строки |
| Каталог файлов на диске | 6.5 МБ, 8 файлов (4 из них — осиротевшие, ждут уборки) | 2.8 МБ, 4 файла |
| Снапшоты CRDT | 728 КБ, 3 шт (самый тяжёлый проект — 711 КБ) | 503 КБ, 175 шт |
| Проектов | 3 | 181 |

Как устроено:

- **`storage.ObjectStore`** (`backend/internal/storage/object_store.go`) — интерфейс из
  пяти методов: `Put`, `Get`, `Delete`, `Stat`, `List(prefix)`. Реализация одна —
  `LocalStore` (файловая система), и её же используют интеграционные тесты.
- **`main.go` всегда берёт `LocalStore`** (`storage.NewLocal(cfg.StorageDir)`); переменные
  `S3_ENDPOINT`/`S3_BUCKET`/`S3_KEY`/`S3_SECRET`/`S3_USE_SSL` в конфиге есть, но ни на что
  не влияют — это заготовка с первой версии.
- Объект-хранилище передаётся в три сервиса: `assets` (запись/чтение/удаление файлов),
  `maintenance` (обход каталога и уборка), `transfer` (перенос архива проекта).
- **Ключ объекта — `<project_id>/<uuid>.<ext>`**; дедупликация идёт не по ключу, а по
  `assets.content_hash` (SHA-256 содержимого): один и тот же файл лежит один раз, а строк
  вложений на него может быть много, и файл удаляется только с последней строкой.
- **Единственный сборщик мусора** — `maintenance.Sweeper`: раз в сутки (и по кнопке в
  админке) делает `List("")` — полный обход каталога — и удаляет файлы, на которые нет
  строк, старше 24 часов (карантин: свежий файл без строки может быть серединой чужого
  импорта).
- **Отдача файлов идёт через приложение**: `GET /api/assets/{id}` (членство в проекте),
  `GET /api/public/assets/{id}` (проект опубликован, иначе 404). Фронтенд тянет файл
  запросом с токеном и подставляет blob-URL (`frontend/src/api/assetObject.ts`) — прямой
  `<img src="/api/assets/…">` не передал бы заголовок авторизации.
- **Развёртывание** — docker compose на одной машине, два тома: `pgdata` и `assets`
  (`/app/storage`). Обновление стенда (`deploy/skyfraze-update.sh`) тома не трогает.
- **Резервных копий нет.** Поиск по `README.md` и `docs/*` не находит ни `pg_dump`, ни
  снимков томов, ни расписания копий: ни база, ни файлы никуда не копируются.

## 2. Что даёт S3/MinIO

1. **Файлы перестают быть частью машины.** Том `assets` — это локальный диск: кончился
   диск, сгорела машина — файлы ушли. Объектное хранилище можно держать на другом хосте.
2. **Отдача без участия приложения.** Presigned-ссылки позволяют браузеру получить файл
   напрямую, не гоняя байты через Go-процесс (сегодня 50-мегабайтный pdf едет через него).
3. **Версионирование и правила хранения.** У S3 есть версии объектов и lifecycle-правила
   (перевести в холодный класс, удалить через N дней).
4. **Несколько инстансов приложения.** Двум-трём копиям backend нельзя смотреть в один
   локальный каталог; общий S3 — можно. Это же путь к «приложение в контейнере без
   состояния» и к горизонтальному масштабированию.
5. **Интерфейс уже готов.** `ObjectStore` с самого начала писался под это: сервисы не
   знают, где лежат байты, и тесты продолжат работать на `LocalStore`.

## 3. Чего S3/MinIO **не** даёт (и почему это здесь главное)

1. **Места он не экономит.** Байты те же. S3 экономит только тогда, когда файлы переезжают
   в холодный класс (у нас 6.5 МБ — экономить нечего) или когда дедупликация была бы
   невозможна без общего хранилища (у нас она уже есть и работает).
2. **Это не резервная копия.** MinIO на том же диске умирает вместе с диском. Копией он
   становится только если стоит на **другой** машине (или это внешний S3). Но ровно того же
   результата можно добиться копированием каталога — без единой строки кода.
3. **Он не спасает от логических ошибок.** «Удалил проект не тот», «импорт затёр»,
   «пережатие испортило картинку» — от этого защищают версии и копии, а не тип хранилища.
4. **Он добавляет обслуживание**: ещё один сервис, его обновления, TLS, ключи доступа,
   мониторинг. На домашнем стенде это реальная цена.

## 4. Что ломается в текущем коде

Это не «может быть», а конкретные места, которые придётся переделать.

### 4.1. Контур доступа к файлам

Сегодня право на файл проверяет приложение: `Open` — членство в проекте, `OpenPublic` —
`projects.is_public`. Публикация и снятие с публикации немедленно закрывают картинки;
это свойство сторожит тест `TestPublicAssetFollowsPublication` (`internal/assets`).

С presigned-ссылками проверить доступ можно **только один раз — в момент выдачи**. Дальше
ссылка работает до истечения срока: «сняли с публикации» перестаёт закрывать уже выданные
ссылки, а сама ссылка пересылается кому угодно. Значит нужно решить:

- **проксировать через приложение** (как сейчас): доступ строгий, но S3 даёт только
  хранение — выигрыша в трафике нет, зато есть лишний сетевой хоп;
- **выдавать короткие presigned-ссылки** (минуты): быстро, но контур доступа слабее, и это
  надо записать в документацию как осознанный компромисс;
- **смешанно**: публичные истории — presigned (кэш на час), приватные — через приложение.

Плюс фронтенд: `assetObject.ts` и `MarkdownBlock` завязаны на blob-URL и авторизацию;
presigned-ссылки — это переделка загрузки картинок в кадре, галерее и фоне.

### 4.2. Lifecycle-удаление несовместимо с правилом уборщика

Модель такая: **истина о файле — строка `assets`**, а уборщик удаляет объект, только если
на него не ссылается ни одна строка (это же правило обслуживает дедупликацию). Правило
«удалить объекты старше N дней» из lifecycle этого не знает и однажды удалит файл, на
который смотрят кадры: в интерфейсе это дырка вместо картинки, в отчёте — «строки без
файла». S3 не умеет «не удаляй, если на объект ссылается строка в Postgres».

Вывод: если включать правила, то **только переходы между классами и версионирование**,
никогда — истечение. Это придётся написать в документации для того, кто будет настраивать
бакет.

### 4.3. `List` перестаёт быть бесплатным и мгновенным

Сейчас `List("")` — обход локального каталога, и интерфейс возвращает **все** объекты
сразу (на 8 файлах это ничто). В S3 это `ListObjectsV2` постранично, по 1000 ключей на
запрос, и каждый запрос — деньги:

| Объектов | Запросов на одну уборку | Память под список |
| --- | --- | --- |
| 100 | 1 | мелочь |
| 10 000 | 10 | ~1 МБ |
| 1 000 000 | 1000 | ~100–150 МБ |

Значит интерфейсу нужен постраничный/потоковый вариант (`Walk(ctx, prefix, func(ObjectInfo)
error)`), а уборщику — обработка «список приехал частями» и повтор при обрыве. Это самая
содержательная часть работы.

### 4.4. Мелочи, которые видно только в коде

- **Карантин по `ModTime`** (24 часа) опирается на время файла; в S3 это `LastModified`
  объекта — работает, но зависит от часов MinIO/сервера: расхождение в сутки сломает
  защиту «не удаляй середину импорта» (или, наоборот, задержит уборку).
- **`Delete` у `LocalStore` игнорирует отсутствие файла** — у S3 `DeleteObject` тоже
  идемпотентен, это совпадает ✓.
- **`Put` получает `size`** и для S3 он как раз нужен: сервер обязан знать длину тела
  (`Content-Length`), иначе загрузка не начнётся. Мы его уже передаём ✓, файл при этом
  остаётся потоковым. Multipart не нужен: он требуется от 5 ГБ (или для докачки), а наш
  предел файла — 50 МБ.
- **Порядок «файл → строка» при импорте и «строка → файл» при удалении** сохраняется, но
  теперь между двумя системами появляется сеть: «положили объект, упали до строки» —
  это уже описанный карантин, а «удалили строку, не смогли удалить объект» — уборщик.
- **Секреты**: `S3_KEY`/`S3_SECRET` в `.env`, права на бакет, TLS до MinIO.
- **Локальная разработка и CI**: поднимать MinIO в compose не обязательно (тесты и e2e
  работают на `LocalStore`), но прод-конфигурацию придётся проверять отдельно — то есть
  нужен либо отдельный job с MinIO, либо честная запись «в CI S3-путь не проверяется».

## 5. Сколько это стоит

| Работа | Оценка | Что входит |
| --- | --- | --- |
| Фаза 1. Резервные копии (нужна в любом случае, см. §6) | 0.5–1 день | `pg_dump` + каталог, копия на вторую машину, расписание, проверка восстановления |
| Фаза 2. `S3Store` за интерфейсом | 2–3 дня | Put/Get/Stat/Delete, постраничный `Walk`, тесты против MinIO, обработка обрывов и таймаутов |
| Фаза 3. MinIO в проде + перенос файлов | 1 день | сервис в compose, бакет, ключи, скрипт переноса с проверкой хешей, откат |
| Фаза 4. Presigned-ссылки и фронтенд | 1–2 дня | решение по контуру доступа, выдача ссылок, переделка `assetObject.ts`/Markdown, TTL |
| Итого | **4.5–7 дней** | плюс постоянное обслуживание ещё одного сервиса |

Денег S3 сам по себе не требует: MinIO — свободный, на своей машине. Внешний S3 стоит
копейки при наших объёмах (гигабайты — центы), но появляется исходящий трафик и зависимость
от чужого сервиса.

## 6. Дешевле и, возможно, достаточно

Это первое, что стоит сделать **вместо** S3, потому что закрывает главный риск (данные
живут в одном месте и никуда не копируются) без изменений в коде:

1. **Копия базы и файлов на вторую машину** (`pg_dump` + `tar`/`rclone` каталога
   `assets`): 0.5 дня, ноль изменений в коде, ноль новых сервисов. Проверка — раз в
   квартал развернуть копию и открыть пару проектов.
2. **NFS/SMB-шара как `STORAGE_DIR`**: файлы физически на другом хосте, приложение об этом
   не знает. Дешевле S3, но заметно медленнее на мелочи и хуже переносит обрывы сети.
3. **Снимки томов средствами хоста** (если стенд — виртуалка): копия всего сразу, включая
   `pgdata`. Плюс: целостность пары «база + файлы» на один момент времени.

## 7. Порог, после которого S3 оправдан

Браться, если выполнено **хотя бы одно**:

- **вторая площадка или вторая копия приложения**: нужен общий каталог файлов для двух
  backend'ов (сегодня один);
- **файлы перестали помещаться в удобную для копирования величину**: практический порог —
  десятки гигабайт (сейчас 6.5 МБ, то есть в тысячи раз меньше);
- **нужна отдача без приложения**: публичные истории с большим трафиком и картинками,
  которые жалко гонять через Go-процесс;
- **нужен холодный класс**: архив проектов, к которому обращаются раз в год (сейчас таких
  объёмов нет);
- **внешний S3 как офсайт-копия** — но это уже подпункт §6.1, и его можно сделать сегодня,
  не трогая код: достаточно `rclone` на каталог.

## 8. План по фазам (если решим делать)

### Фаза 0. Измерение перед решением — сделано этим документом

Числа выше. Повторить замер через полгода: если каталог вырос меньше чем на порядок,
пункт «объём» не наступил.

### Фаза 1. Резервные копии — **делать независимо от S3**

- `deploy/backup.sh`: `pg_dump -Fc` базы и `tar` каталога `assets` в один каталог с датой,
  плюс `rclone`/`scp` на вторую машину (или внешний S3 — тот же `rclone`).
- systemd-таймер раз в сутки, ротация (7 дней / 4 недели), лог.
- **Проверка**: восстановить копию на отдельной базе и открыть проект с картинками.
  Копия, которую не восстанавливали, копией не считается.
- Документ `docs/backups.md`: что копируется, куда, как восстановить.

### Фаза 2. `S3Store` за тем же интерфейсом

- `backend/internal/storage/s3.go` (`minio-go` или AWS SDK v2 — решить по зависимостям;
  предпочтение `minio-go`: один клиент и для MinIO, и для S3).
- **Постраничный обход**: добавить в `ObjectStore` метод `Walk(ctx, prefix, fn)`, оставив
  `List` для тестов и мелких задач. Уборщик переводится на `Walk` — иначе на большом
  бакете он соберёт весь список в память.
- Выбор реализации в `main.go` по конфигу (`S3_ENDPOINT` задан → S3, иначе локально) —
  переменные уже есть.
- Тесты: общие для обеих реализаций (один набор сценариев, два бэкенда), плюс отдельный
  job в CI с MinIO — или честная запись в документации, что S3-путь проверяется руками.

### Фаза 3. Перенос стенда

- MinIO в `docker-compose.prod.yml`, бакет создаётся при старте, ключи в `.env`.
- Скрипт переноса: пройти `assets` из базы, залить объекты, **сверить размеры и хеши**,
  только потом переключить конфиг. Том `assets` не удалять минимум месяц — это откат.
- Откат: убрать `S3_ENDPOINT`, вернуть `STORAGE_DIR`; строки в базе не меняются, ключи те
  же, поэтому приложение просто снова читает с диска.

### Фаза 4. Presigned-ссылки — только если реально нужны

Отдельное решение по контуру доступа (§4.1), с явной записью компромисса в
`docs/architecture.md` и тестами: «сняли с публикации → новая ссылка не выдаётся, старая
живёт не дольше TTL».

## 9. Что проверять, чтобы не сломать уже сделанное

Инварианты, которые обязаны сохраниться при любом хранилище (сегодня их стерегут тесты):

1. **Дедупликация по содержимому**: одна картинка в двух проектах — один объект, две
   строки; удаление одной строки файл не трогает, удаление последней — убирает.
2. **Уборка**: старый файл без строк удаляется, свежий (идёт импорт) — нет; строка без
   файла только попадает в отчёт и никогда не удаляется автоматически.
3. **Права**: файл приватного проекта не отдаётся постороннему; снятие с публикации
   закрывает публичную отдачу немедленно (`TestPublicAssetFollowsPublication`).
4. **Отказ импорта/загрузки** не оставляет ни файлов, ни строк.
5. **Пережатие и квота** продолжают работать: они ходят через `ObjectStore` и не должны
   знать, где лежат байты.
6. **Отчёт о хранилище** (`/api/admin/storage`) продолжает сверять каталог с базой — с
   S3 это `Walk`, и «пропавшие файлы» должны считаться так же.

## 10. Решение

**Пока не делать.** Обоснование в трёх строках: места это не экономит (вложения стенда —
5.48 МБ), текущий стенд — одна машина и один инстанс приложения (общий каталог не нужен),
а главный риск — отсутствие резервных копий — закрывается за полдня и без единой строки
кода. S3/MinIO вернуть в работу, когда сработает любой порог из §7; к тому моменту
интерфейс `ObjectStore` уже готов, поэтому основная работа сведётся к фазе 2.

Вместо S3 в бэклоге остаётся:

1. **Резервные копии** (`deploy/backup.sh` + `docs/backups.md`, проверенное
   восстановление) — 0.5–1 день, делать первым;
2. предупреждение о тяжёлых снапшотах в отчёте хранилища (мелочь, полчаса);
3. всё остальное из `docs/storage-compression.md`, §5 — там уже сделано.
