# SkyFraze — Architecture

## High-level

```
[Browser]                                              [Server]
  React app                                             Go backend
  ├── REST client ──────────────HTTPS────────────► chi router
  │
  ├── Yjs WebSocket client ───WSS (JWT)──────────► collab hub
  │
  ├── Three.js scene (canvas) ◄── GET events/state ───
  │
  └── Asset upload ──POST /api/assets (multipart)──► storage svc ──► filesystem
                                                        └─► postgres assets table
```

## Phase 1 decisions

| Решение | Почему |
|---|---|
| Postgres 15 (вместо 16) | Образ `postgres:15-alpine` доступен локально в этом окружении; `postgres:16-alpine` нет. Семантически одно и то же. |
| Filesystem ObjectStore (вместо MinIO) | Образ `minio/minio` недоступен. `internal/storage.ObjectStore` — единая абстракция; MinIO добавим в Phase 2 без изменения контракта. |
| npm (вместо pnpm) | pnpm не установлен; npm есть. Vite-проект работает идентично. |
| C++ НЕ участвует в Phase 1 | См. план — C++ остаётся в Phase 3 (native renderer). |
| Three.js для 3D | Полноценный WebGL; события = 3D-объекты. |
| Свой Yjs-relay на Go | Меньше языков в стеке; полный контроль над auth/persistence. |

## Domain model (Postgres)

```sql
users                (id, email, password_hash, display_name, created_at)
projects             (id, owner_id, title, description,
                      is_public, public_slug, published_at, views_count, ...)
team_memberships     (project_id, user_id, role)          -- owner > editor > viewer
invitations          (id, project_id, email, token, role, expires_at, accepted_at)
events               (id, project_id, parent_id, depth, position,
                      title, body, event_date, created_by, updated_by, ...)
project_event_state  (project_id PK, yjs_state BYTEA, revision, updated_by, updated_at)
project_views        (id, project_id, visitor_key, viewed_on)  -- дедуп: 1/сутки
project_ratings      (project_id, user_id, stars 1..5, ...)    -- PK(project_id,user_id)
assets               (id, project_id, owner_id, filename, mime, size, s3_key,
                      kind, content_hash, ...)
event_assets         (event_id, asset_id)                 -- M2M
sessions             (id, user_id, refresh_token_hash, expires_at)
schema_migrations    (version PK, applied_at)
```

`events` — по строке на событие: `parent_id` (самоссылочный FK `ON DELETE
CASCADE`), `depth` (0..8, проверяется CHECK), `position` (0..n-1 внутри группы
соседей). CRDT-снапшот проекта живёт отдельно в `project_event_state` и
версионируется (`revision`) — раньше он лежал в `events.yjs_state`, из-за чего
`events` содержала одну строку-заглушку на проект («фантомное событие»).

`assets.content_hash` (SHA-256 содержимого, миграция 0007) — то, что делает файл
одним на несколько строк: одинаковое содержимое не пишется в хранилище дважды, а
`assets.s3_key` у таких строк общий (поэтому уникальность ключа снята). Имя файла,
владелец и проект остаются у каждой строки свои. Файл удаляется только тогда, когда
исчезла последняя ссылка на его ключ (`assets.Service.DeleteUnreferencedFiles`), и
это же правило — единственный сборщик мусора в хранилище (`maintenance.Sweeper`).

## Публичная лента: контур доступа

Три уровня видимости, и переход между ними — только явное действие владельца:

| Уровень | Кто видит | Как попасть |
|---|---|---|
| закрытый (по умолчанию) | команда проекта | ничего не делать |
| публичный | любой, без входа | `POST /api/projects/{id}/publication {"is_public":true}` (только owner) |
| снят с публикации | никто, кроме команды | тот же ручка с `false` |

Инварианты, которые нельзя нарушать при доработках:

- **Источник истины о видимости — только `projects.is_public`.** Любая выборка в
  `internal/store/store_feed.go` обязана содержать это условие; членство в проекте
  публичным чтением не проверяется вообще.
- **Неопубликованное неотличимо от несуществующего**: закрытый проект по slug даёт
  404, а не 403, иначе перебором можно узнать, какие истории существуют.
- **Публичные ручки не пишут содержимое.** `/api/public/*` умеет только читать и
  ставить оценку (оценка — отдельная таблица, не содержимое истории).
- **Снятие с публикации закрывает и файлы**: `/api/public/assets/{id}` проверяет
  `is_public` проекта-владельца, поэтому картинки перестают отдаваться вместе с историей.
- **`public_slug` выдаётся один раз** и не меняется ни при снятии, ни при повторной
  публикации: внешние ссылки не должны ломаться.
- **Просмотры дедуплицируются** уникальным индексом
  `project_views (project_id, visitor_key, viewed_on)`; `projects.views_count`
  инкрементируется в той же транзакции, что и вставка строки, иначе счётчик
  расходится с числом просмотров.
- **Оценка одна на пользователя** (`PRIMARY KEY (project_id, user_id)`), звёзды 1..5
  (CHECK), автор не оценивает свою историю (403 в `feed.Service.Rate`). Среднее и
  количество считаются на чтение — денормализации нет, значит нет и расхождений.

Публичная страница `/s/{slug}` не подключается к WebSocket и не вызывает ни одной
ручки записи: ответ `GET /api/public/stories/{slug}` разворачивается в локальный
`Y.Doc` (`frontend/src/components/timeline/publicDoc.ts`), из которого читает та же
стадия, что и в редакторском режиме.


## Миграции

`backend/migrations/*.up.sql` вшиты в бинарь (`migrations.FS`) и применяются
`platform.RunMigrations` по одной, в транзакции, с отметкой в `schema_migrations`.

- каждый файл применяется ровно один раз; повторный запуск — no-op;
- файлы должны быть идемпотентными (`IF NOT EXISTS` / `OR REPLACE`) и **без
  собственных `BEGIN`/`COMMIT`** — транзакцию открывает раннер;
- многостейтментный SQL выполняется через simple-протокол (`PgConn().Exec`),
  потому что extended-протокол pgx его не принимает;
- новая миграция = новый файл `NNNN_name.up.sql` (+ `.down.sql` для отката).
  Раньше раннер был no-op: `embed` объявлялся в `cmd/server` с паттерном
  `migrations/*.sql`, поэтому `fs.ReadDir(".")` возвращал директорию, и ни одна
  миграция не применялась — схема на чистой БД не создавалась вообще.

## Folder boundaries

- `events` — CRDT-документ + серверная модель дерева событий (валидация, CRUD)
- `teams` отделён от `projects`
- `assets` — отдельный сервис, общается с `storage` напрямую
- `collab` — изолированный WebSocket-хаб
- `platform` — config, logger, db pool, раннер миграций

## Иерархия событий (вложенность)

Два слоя, у каждого своя роль:

| Слой | Что хранит | Кто валидирует |
|---|---|---|
| CRDT (`Y.Array('events')`, поле `parent_id`) | живое совместное редактирование, realtime | `frontend/src/collab/eventTree.ts` (нормализация при отрисовке) |
| Postgres (`events.parent_id`/`depth`/`position`) | серверная модель: проверки, права, каскадное удаление, выдачи API | `backend/internal/events` (`NormalizeTree`, `MaxDepth = 4`) |

Клиент после локальных правок проецирует дерево на сервер
(`PUT /events/tree`), сервер проверяет структуру (цикл, отсутствующий родитель,
самоссылка, дубликат id, глубина > `MaxDepth`, чужой проект) и возвращает
каноническое дерево. Если структура отклонена (400), клиент приводит CRDT к
нормализованному виду (`yRepairHierarchy`: сироты и участники циклов → корень)
и повторяет проекцию один раз — так клиент и сервер сходятся к одному дереву.

Правила, которые держит сервер:

- порядок соседей — `position` 0..n-1, переиндексация при переносе и удалении;
- перенос запрещён «в себя» и «в собственного потомка»
  (`DescendantsIDs`), глубина поддерева пересчитывается целиком;
- удаление главы каскадом удаляет под-события (FK), позиции соседей
  переиндексируются;
- `event_assets` не теряются: при синхронизации дерева строки не
  пересоздаются, а upsert'ятся по стабильному id.

## REST API событий

| Метод | Путь | Роль | Назначение |
|---|---|---|---|
| GET | `/api/projects/{id}/events` | viewer+ | дерево событий |
| POST | `/api/projects/{id}/events` | editor+ | создать событие/под-событие (`parent_id`) |
| PATCH | `/api/projects/{id}/events/{eventId}` | editor+ | title/body/event_date |
| PUT | `/api/projects/{id}/events/{eventId}/parent` | editor+ | перенос (`parent_id`, `position`) |
| DELETE | `/api/projects/{id}/events/{eventId}` | editor+ | удалить с потомками |
| PUT | `/api/projects/{id}/events/tree` | editor+ | идемпотентная проекция дерева целиком |
| GET | `/api/projects/{id}/events/state` | viewer+ | CRDT-снапшот (+ `X-Skyfraze-Revision`) |
| PUT | `/api/projects/{id}/events/state` | editor+ | запись снапшота от базовой ревизии |

Ошибки: `400` — невалидная структура/поля, `403` — роль ниже требуемой,
`404` — нет проекта/события, `409` — конфликт ревизии снапшота,
`428` — не передан `X-Skyfraze-Base-Revision`.

Снапшот версионируется: запись принимается только от той ревизии, которую
клиент видел последней. При конфликте клиент перечитывает состояние, мержит
его в свой Yjs-документ и повторяет запись (CRDT не теряет правки) — это
заменяет прежнюю схему «последний писатель затирает всех».

Безопасность: запись в таймлайн требует роли `editor` (раньше `viewer` мог
перезаписать весь снапшот), а WebSocket проверяет `Origin` по `CORS_ORIGINS`
(пустой Origin пропускается — это не-браузерные клиенты, их защищает токен).

## Перенос проекта между инсталляциями

`internal/transfer` собирает и разбирает один ZIP-архив: `manifest.json` (мета + дерево
событий + список вложений), `state.bin` (CRDT-снапшот) и `assets/<id>` (файлы).

```sql
-- импорт пишет те же таблицы, что и обычная работа, но с сохранением id:
projects             (новый id; владелец — тот, кто импортировал)
events               (id/parent_id/depth/position/title/body как в архиве)
assets               (id как в архиве, s3_key = <новый project_id>/<asset_id>)
project_event_state  (yjs_state как в архиве, revision = 1)
```

Инварианты:

- **Импорт никогда не пишет в существующий проект.** Он всегда создаёт новый; при любой
  ошибке за собой убирает (удаляет проект и уже записанные файлы).
- **id событий и вложений сохраняются.** CRDT-снапшот — бинарный Yjs-update, ссылки
  внутри него переписать на сервере нельзя. Поэтому повторный импорт того же архива
  распознаётся по уже существующим id (`ExistingEventIDs` / `ExistingAssetIDs`) и
  возвращает `409 ErrAlreadyImported`, а не «перезапись» чужого проекта.
- **Архив проверяется до записи**: формат/версия, размер (200 МБ), лимиты (5000 событий,
  500 вложений), размер каждого файла (50 МБ) и структура дерева — теми же правилами
  `events.NormalizeTree`, что и обычная синхронизация (циклы, глубина, сироты).
- **Дерево вставляется в порядке «родители раньше детей»** (это гарантирует
  `NormalizeTree`): на этом держится FK `events.parent_id`.
- **Просмотры, оценки и публикация не переносятся** — это свойства инсталляции, а не
  проекта; на новом стенде проект приезжает закрытым (`is_public = false`).
- **Экспорт — `viewer+`, импорт — любой вошедший.** Читатель и так видит всё содержимое
  проекта (события, вложения, снапшот), поэтому выгрузка не расширяет его права.

Отдельная деталь: проект без CRDT-снапшота (созданный через API или импортированный из
архива такого проекта) при первом открытии в редакторе засевается из реляционного дерева
(`yprovider`: если `events.length === 0`, тянем `GET /events` и наполняем Y.Array). Иначе
стадия, которая читает только CRDT, показывала бы пустой таймлайн при непустой базе.

## Обновление стенда из GitHub

Контур обновления разделён на две половины — и это осознанно:

| Половина | Где живёт | Что делает |
|---|---|---|
| Проверка и заявка | `internal/update` (контейнер) | спрашивает GitHub Releases API, сравнивает версии, пишет `request.json` в общий каталог |
| Применение | `deploy/skyfraze-update.sh` (хост) | `git fetch` → `checkout` тега → `docker compose up -d --build` → health-check → пишет `status.json`/`update.log` |

Инварианты:

- **Веб-процесс не получает `docker.sock`.** Пересборка выполняется на хосте: контейнеру с
  сокетом Docker соответствовал бы root на хосте, а страница обновления доступна по HTTP.
- **Связь — только через каталог состояния** (`update-state/`, смонтирован в контейнер):
  админка пишет `request.json`, хост пишет `status.json` и `update.log`. Никаких RPC.
- **Заявка сразу помечается `requested`.** Иначе до старта скрипта страница показывала бы
  «ничего не происходит», и админ нажимал бы кнопку повторно (повторная заявка во время
  `requested`/`running` отклоняется с 409).
- **Версия сравнивается с тегом релиза** (`isNewer`): `dev` и пустая версия старее любого
  релиза, суффикс сборки (`0.2.1+3-gabc123`) не считается новой версией, канал `stable`
  игнорирует предрелизы. Ответ GitHub кэшируется на 10 минут, `?force=1` — «Проверить сейчас».
- **Версия и коммит попадают в бинарь** через `-ldflags "-X main.version -X main.commit"`
  (build args `SKYFRAZE_VERSION`/`SKYFRAZE_COMMIT`, их выставляет скрипт обновления) — иначе
  страница не знала бы, что именно запущено.
- **Обновление не трогает данные**: `.env` и `update-state/` в `.gitignore`, а проекты,
  вложения и пользователи живут в docker-томах (`pgdata`, `assets`).

Первый запуск на уже развёрнутом стенде требует, чтобы каталог был git-клоном: инструкция
в README (раздел «Обновление стенда из GitHub»).

## Администрирование развёртывания

Инсталляция по умолчанию **закрыта**: самостоятельная регистрация запрещена, доступ —
по заявке. Администратор задаётся развёртыванием и управляет только входом: содержимое
чужих проектов ему недоступно.

```sql
users                 (id, email, password_hash, display_name, is_admin, ...)
app_settings          (key PK, value, updated_at, updated_by)   -- registration_mode
registration_requests (id, email, display_name, password_hash, message,
                       status pending|approved|rejected, note,
                       created_at, decided_at, decided_by)
```

Инварианты:

- **Режим регистрации — одна запись** `app_settings.registration_mode`:
  `request` (по заявке, дефолт миграции) | `open` (свободная). `POST /api/auth/register`
  в режиме `request` отвечает 403; форма на `/register` заранее спрашивает режим
  у `GET /api/auth/config` и показывает либо регистрацию, либо заявку.
- **Значение из env `REGISTRATION_MODE` — только стартовое.** Оно применяется, пока
  настройку не менял администратор (`app_settings.updated_by IS NULL`). После первого
  решения админа env не перебивает его: иначе развёртывание откатывало бы выбор человека.
- **Администратор — `users.is_admin`.** Назначается `ADMIN_EMAILS` (права выдаются и
  существующим, и новым — при входе), а если админов нет вообще, им становится первый
  зарегистрированный: инсталляция не должна оставаться без способа управлять входом.
- **Окно первого администратора.** Прямая регистрация разрешена, если режим `open`,
  ИЛИ в базе ещё нет ни одного пользователя (`bootstrap`), ИЛИ email входит в
  `ADMIN_EMAILS`. Первые два условия закрывают «курицу и яйцо»: при режиме «по заявке»
  на пустой инсталляции одобрять заявки было бы некому, а админ из окружения должен
  уметь завести себе аккаунт в любом случае. `GET /api/auth/config` отдаёт
  `{registration_mode, bootstrap}`, и форма регистрации по этому флагу показывает либо
  обычную форму («Первый администратор»), либо заявку.
- **Развёртывание на сервере — `docker-compose.prod.yml`.** Отдельный файл, потому что
  dev-версия публикует `5432:5432`: на сервере с системным Postgres или mailcow контейнер
  не поднимется из-за занятого порта. В prod-версии база доступна только backend'у по
  внутренней сети, а порт UI задаётся `SKYFRAZE_PORT`.
- **Заявка хранит хэш пароля.** Одобрение создаёт аккаунт с этим паролем
  (`store.ApproveRegistrationRequest` — одна транзакция: пользователь + статус заявки),
  поэтому почтовые ссылки не нужны. Одна активная заявка на email — частичный
  уникальный индекс `(lower(email)) WHERE status='pending'`.
- **Состояние заявки объясняется только владельцу пароля.** `auth.Login` сообщает
  «на рассмотрении»/«отклонена» лишь после успешной проверки пароля заявки; иначе по
  одному email можно было бы узнать, кто подавал заявку.
- **Повторное решение по заявке невозможно**: `DecideRegistrationRequest` и
  `ApproveRegistrationRequest` работают только со статусом `pending`, иначе 404 —
  двойное одобрение не создаст второго пользователя.

| Метод | Путь | Доступ |
|---|---|---|
| GET | `/api/auth/config` | аноним |
| POST | `/api/auth/registration-requests` | аноним (202) |
| GET/PATCH | `/api/admin/settings` | админ |
| GET | `/api/admin/registrations?status=` | админ |
| POST | `/api/admin/registrations/{id}/approve` \| `/reject` | админ |
| GET | `/api/admin/users` | админ |

## REST API публичной ленты

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/public/feed?sort=new\|rating\|views&limit=&offset=` | аноним | лента опубликованных историй |
| GET | `/api/public/stories/{slug}` | аноним | история: карточка, вложения, CRDT-снапшот (или дерево `events`); +1 просмотр |
| POST | `/api/public/stories/{slug}/rating` | вход | поставить/заменить оценку `{"stars":1..5}` |
| DELETE | `/api/public/stories/{slug}/rating` | вход | снять свою оценку |
| GET | `/api/public/assets/{id}` | аноним | файл опубликованного проекта (иначе 404) |
| POST | `/api/projects/{id}/publication` | **только owner** | `{"is_public":true\|false}` |

Ошибки: `400` — звёзды вне 1..5 или неизвестная сортировка, `401` — оценка без токена,
`403` — самооценка автора или публикация не владельцем, `404` — история не найдена
(в том числе снятая с публикации: закрытое неотличимо от несуществующего).

Ответ `GET /api/public/stories/{slug}`:

```json
{
  "story":   { "id": "...", "title": "...", "slug": "...", "author": "Имя",
               "views": 12, "rating_avg": 4.5, "rating_count": 2,
               "cover_asset_id": "...", "published_at": "..." },
  "assets":  [ { "id": "...", "mime": "image/png", "kind": "image", "filename": "..." } ],
  "state":   "<base64 CRDT-снапшота; пусто, если снапшота нет>",
  "events":  [ { "id": "...", "parent_id": null, "position": 0, "title": "...", "body": "..." } ],
  "my_rating": 4
}
```

`state` приоритетнее `events`: снапшот — источник истины для кадров (тексты,
вложения, фон). Строки `events` приходят только у проектов, которые ни разу не
открывали в редакторе, — это запасной вариант, а не второй источник правды.


## Скролл и layout

Приложение использует layout-грид: `.layout` (`header` + `main`), где скроллится
именно `main` (`.layout main { overflow: auto }`), а не window. Поэтому любая
логика, читающая `window.scrollY` или вешающая слушатель на `window` без
capture, молча не работает.

- `frontend/src/components/timeline/scrollRoot.ts` — находит фактический
  scrollport и даёт метрики (`visibleBox`, `scrollProgress`, `subscribeToAnyScroll`).

## Сценический таймлайн

Таймлайн собран по композиции `deps/scroll-world/skills/scroll-world/references/index-template.html`
(движок scroll-world), но без видео-цепочки и без WebGL: скролл переключает
кадры и текстовые вставки, а не «везёт» контент вверх.

**Кадр = событие.** Глава — кадр, и каждое её под-событие — тоже отдельный
развёрнутый кадр (нумерация по ветке `01.1`, `01.1.1`). Поэтому внутри главы
под-события показываются по одному, полностью, прежде чем трек перейдёт к
следующей главе. Веса окон: глава `1`, под-событие `0.9`, под-шаг `0.75`
единиц трека, кроссфейд внутри кадра — `TRANSITION_BAND`.

| Слой | Класс | Что делает |
|---|---|---|
| прогресс | `.sf-progress` | полоса 3px сверху = прогресс трека |
| верхняя панель | `.sf-topbar` | название проекта, пилюли глав, действия; ≤1280px пилюли заменяются чипами |
| небо | `.sf-sky` | градиент от акцента кадра, свечение, дрейф-частицы |
| кадры | `.sf-stage` + `.sf-scene` | активный кадр + предыдущий (кроссфейд): фон кадра и параллакс |
| копирайт | `.sf-copylayer` + `.sf-copy` | номер кадра, eyebrow, заголовок, текст, мета-чипы, галерея картинок, превью вложенных, «назад / дальше» |
| маршрут | `.sf-route` | карточка справа: рельса глав (пройденные/текущая/будущие) + ветка кадров активной главы; подписи видны постоянно, длинные названия переносятся до двух строк (`title` — полный текст); ≤1280px заменяется чипами |
| подсказка | `.sf-hint` | гаснет, как только начался скролл |
| трек | `.sf-track` | единственный элемент в потоке; его высота = длина скролла |

Раскладка и скролл-мэппинг — `frontend/src/components/timeline/timelineModel.ts`
(чистые функции + тесты): `buildTimelineModel` собирает кадры из дерева,
`resolveScrollState` переводит прогресс в `{chapterIndex, frameIndex,
frameLocal, transition}`.

### Фон кадра настраивается на событии

В CRDT события лежат `bg_kind` (`inherit` | `tone` | `asset`), `bg_tone` (hex) и
`bg_asset` (id ассета). При сборке модели фон наследуется от родителя:
`inherit` берёт фон главы, `tone` рисует мягкий градиент, `asset` ставит
картинку из вложений события; если не задано ничего — процедурная иллюстрация.
Настройка живёт в редакторе (блок «Фон кадра»).

Стадия — просмотр и навигация: она **не** переключает редактор и ничего не
меняет. Все правки идут через `EditorsPanel`, который сообщает странице об
изменении (`onChanged`), а та проецирует дерево на сервер. Создание события не
уводит стадию к новому кадру — пользователь остаётся в редакторе.

Ассеты отдаются только авторизованным запросом (`GET /api/assets/{id}`), а тег
`<img>` заголовок не передаёт: файлы скачиваются через `src/api/assetObject.ts`
и подставляются как blob-URL (кэш на сессию). Прямые ссылки на ассеты давали
401 — из-за этого картинки не отображались ни в галерее кадра, ни как фон.

Навигация по кадрам сквозная: «назад / дальше» в копирайте идут через весь
таймлайн (в том числе на предыдущую/следующую главу), а маршрут справа и чипы
прыгают к любому кадру.

Стадия активна, только пока трек занимает вьюпорт: под редакторами fixed-слои
уходят в `data-stage="idle"`. Программные прыжки уважают
`prefers-reduced-motion` (без smooth-скролла).

Темы: тёмная (по умолчанию) и светлая кремово-мятная; переключаются атрибутом
`data-theme` на `<html>` (`frontend/src/store/theme.ts`, кнопка в `Header`),
все цвета — токены, тема запоминается в localStorage.

## Ошибки интерфейса: плашка с выходами, а не текст исключения

Правило проекта: пользователь **никогда** не видит сырое сообщение вида
`TimeoutError: Request timed out: GET http://…`. Любая ошибка загрузки или действия
превращается в плашку с тремя обязательными частями:

1. **что случилось по-человечески** — `frontend/src/lib/apiError.ts` (`describeApiError`)
   классифицирует ошибку: нет связи, таймаут, 5xx, 401/403/404/409, прочее;
2. **что делать** — подсказка («связь могла прерваться во время обновления сервера»);
3. **куда пойти** — кнопка «Повторить» для временных сбоев и минимум одна ссылка на
   доступную страницу (`← В ленту`, «Мои проекты», «К проектам»).

Компонент — `frontend/src/components/ErrorBanner.tsx`; он стоит на страницах ленты,
публичной истории, списка проектов, таймлайна проекта и в админке. Классификатор
покрыт юнит-тестами (`apiError.test.ts`), а e2e `tests/public-feed.ts` проверяет
поведение при обрыве сети: запрос абортится — плашка появляется, содержит ссылку,
а «Повторить» после восстановления связи открывает историю.

Публичные запросы дополнительно повторяются сами (`retry` в `api/feed.ts`) и имеют
увеличенный таймаут (25 c на историю: ответ несёт CRDT-снапшот). Это важно, потому
что перезапуск/пересборка контейнера на несколько секунд рвёт соединение — без повтора
и плашки это выглядело как «история не открылась» с непонятной ошибкой.



В проекте есть скилл `.dsh/skills/ui-visual-audit` с раннером
`scripts/visual-audit.ts`: он проходит экраны во всех вьюпортах и темах, снимает
скриншоты и считает геометрию/переполнение/hit-test/контраст, а затем прогоняет
функциональную матрицу (проекты, иерархия, ассеты, темы, роли, realtime CRDT,
публичная лента — доступ, просмотры, оценки). Публичные экраны проверяются дважды:
как вошедший пользователь и в отдельном анонимном контексте. Отчёт —
`_audit_out/visual-report.md` с указанием файла, который надо править.

Правила, которые раннер проверяет и которые легко сломать:

- ассеты отдаются только авторизованным запросом → в `<img>` всегда blob-URL
  (`src/api/assetObject.ts`), а не `/api/assets/{id}`; на публичных страницах —
  `/api/public/assets/{id}` (доступен только для опубликованных проектов);
- **публичность проверяется только по `projects.is_public`** — ни лента, ни
  публичная страница, ни публичные файлы не должны опираться на членство в проекте
  или на «угадываемые» id: неопубликованное отдаёт 404 так же, как несуществующее;
- nginx `client_max_body_size` ≥ лимита бэкенда (50 МБ), иначе загрузка фотографий
  молча падает с 413;
- `index.html` отдаётся с `Cache-Control: no-store`, иначе после пересборки браузер
  держит старый бандл;
- fixed-слои стадии в `idle` получают `visibility: hidden` — иначе они крадут клики
  у блока редакторов;
- первичные кнопки используют `--accent-strong` (белый текст на `--accent` давал
  контраст 2.5:1), активные пилюли — тёмный текст на пастельном акценте;
- интерактивные элементы на мобильном не меньше 34px по высоте (включая
  сортировку ленты, «Читать →» и публичную ссылку проекта);
- базовый кегль `html` — 16px: `rem` в панели рассчитан от него, при 14px подписи
  навигации и маршрута выходили ~11px и не читались;
- навигация по главам (`.sf-route`) показывает подписи постоянно и переносит длинные
  названия вместо обрезки многоточием — «мелкое и нечитаемое» поле перехода глав
  проверяется в `frontend/tests/scrollytelling.ts` (кегль ≥ 12px, высота строки ≥ 32px,
  клик по строке меняет кадр).

## Маршруты проектов

`/api/projects` обслуживается двумя точками входа chi: `Mount("/api/projects", ...)`
для коллекции (`GET /`, `POST /`) и param-поддерево `Route("/api/projects/{id}", ...)`
для одиночного проекта и под-ресурсов (`members`, `invitations`, `events`, `assets`).
Param-ветка специфичнее wildcard от `Mount`, поэтому CRUD одиночного проекта
(`GET/PUT/DELETE /api/projects/{id}`) регистрируется внутри param-поддерева в
`backend/cmd/server/main.go`. Дублирование этих роутов в `projects.Handler.Routes`
делает их недостижимыми (так `GET /api/projects/{id}` отдавал 404).
