# Realtime-правки в редакторе SkyFraze: состояние, механизмы, рекомендация

Документ описывает, как сейчас устроена совместная правка таймлайна, где именно
теряются изменения, какие механизмы realtime существуют и что из них имеет смысл
внедрять в SkyFraze. Опирается только на код репозитория (`C:\Projects\SkyFraze`).

## 2. Где реально теряются или перетираются правки

Разбор ниже — исходное состояние на момент аудита; пункты, закрытые фазами 0–2, помечены.

1. **Двое в одном тексте.** `title`/`body` были скалярами `Y.Map`: Yjs даёт LWW на ключ,
   победившая запись побеждала целиком, и набранный в это же время текст второго автора
   исчезал без следа.
   **Закрыто (Фаза 2):** текст живёт в `Y.Text` (`collab/text.ts`), правки применяются
   минимальным дифом, живой тест `tests/text-merge.ts` проверяет, что при одновременном
   наборе двух авторов не теряется ни один символ.
   Остаётся списковое: `assets` мержатся как union, поэтому одновременное «открепить» у
   одного и «прикрепить» у другого воскрешает удалённый id (`EditorsPanel.tsx`) —
   отдельный шаг, если понадобится.
2. **Один без WebSocket.** Соединение не поднимается (прокси без Upgrade, сеть, блокировка) —
   `yprovider.ts` логирует и живёт дальше. Такой клиент не видит чужих правок
   и никому не отдаёт свои: они уйдут только в БД при следующем успешном REST-сохранении,
   а до этого браузер остаётся единственным местом, где они есть.
   **Частично закрыто:** реконнект с бэкоффом (0.1) возвращает realtime сам, а запас в
   `localStorage` (0.4) страхует уход со страницы — потери на закрытии вкладки больше нет.
3. **Открытое модальное окно.** `MarkdownEditor` держал локальную копию (`useState(value)`)
   и отдавал её только по `onSave`. Пока окно открыто, чужие
   изменения `body` не были видны, а «Сохранить» затирало их локальной копией.
   **Закрыто (0.2):** политика вынесена в `collab/liveText.ts` — черновик не подменяется,
   пришедшая версия принимается молча, если не печатают, иначе показывается полоса
   с кнопкой «взять версию соавтора».
4. **Устаревший клиент с `PUT /events/tree`.** Проекция строится из
   **локального** CRDT и уходила полной заменой без ревизии: клиент,
   который давно не получал апдейты, сносил чужие строки в реляционной модели.
   **Закрыто (0.5):** проекция требует `X-Skyfraze-Base-Revision` (428 без него, 409 при
   устаревшей базе), проверка идёт в одной транзакции с заменой дерева.
5. **Закрытие вкладки.** `pagehide`-путь шлёт keepalive-PUT и
   **не обрабатывал 409**: при конфликте последняя правка молча терялась. Запись шла
   только если `wsOpened && canWrite()` — клиент без WS не сохранял на уходе вообще.
   **Закрыто (0.4):** состояние и база сначала кладутся в `localStorage`, запись на уходе
   больше не зависит от `wsOpened`, а запас применяется при следующем открытии проекта
   (`Y.applyUpdate`) и снимается только после подтверждённой записи.
6. **Две вкладки одного пользователя.** Между вкладками не было ни `BroadcastChannel`, ни
   общего состояния: правка в одной была видна в другой только после перезагрузки.
   **Закрыто (0.3):** `collab/broadcast.ts` — канал на проект, апдейты с меткой вкладки,
   защита от эха (origin `'peer'` не пересылается назад).
7. **Масштаб.** При 20 одновременных правках каждый клиент отправляет полный снапшот
   раз в 300 мс (`yprovider.ts:save`) плюс страховочный `setInterval` 30 с
   (`yprovider.ts:safetyNet`), и все они конкурируют за одну ревизию: серия 409 →
   merge → повтор. Снапшот в `project_event_state` хранится целиком и без компакции
   (`backend/migrations/0002_events_hierarchy.up.sql:52-58`), то есть монотонно растёт.
   **Остаётся: лечится Фазой 3.**

## 3. Механизмы realtime для текстового редактора

### 3.1. Сравнение механизмов

| Механизм | Как работает | Что даёт | Чем платим | Подходит SkyFraze? |
| --- | --- | --- | --- | --- |
| Yjs CRDT: `Y.Text` вместо скаляра | Правки — CRDT-операции: `Y.Text` вставляет символы с позиционными id, вставки двух авторов сохраняются обе, а не «кто последний» | Посимвольный merge текста, нет «затёртых» абзацев | Правка схемы данных (см. §4.1), нужно писать только в `Y.Text` | **Да, базовый путь** |
| Awareness (`y-protocols/awareness`) тем же WS | Отдельный, не сохраняемый в документе канал состояний: кто где, курсор, «печатает…» | Присутствие и курсоры; чистится при отключении | Фильтрация типов сообщений на клиенте, TTL-очистка, UI участников | **Да, дёшево и заметно** |
| Серверный merge + персистенция из hub | Сервер сводит апдейты клиентов и сам пишет снапшот по интервалу, а не на каждое нажатие | Один писатель на комнату, нет шторма 409, реже запись в БД | Нужна Yjs-реализация на Go: сейчас заглушка `hub.go:284-290` | **Да, но после `Y.Text`** |
| Operational Transform (ShareDB/OT-сервер) | Клиент шлёт операции, сервер трансформирует конкурентные и рассылает согласованный порядок; документ живёт на сервере | Детерминированный порядок, серверный авторитет, готовые курсоры | Второй механизм конфликтов рядом с CRDT, новый обязательный сервис, своя OT на Go для дерева | **Нет, переусложнение** |
| Presence/awareness отдельным каналом | То же, что awareness, но своей схемой сообщений поверх `/collab` | «Кто сейчас здесь», кто в каком событии, «печатает…» | Своя схема + сервер не должен писать это в снапшот | **Да, если не брать y-protocols** |
| Сервер-авторитетная модель: блокировки/аренда поля | Поле на TTL принадлежит одному редактору, остальные read-only | Предсказуемость, нет «невидимых» merge-эффектов, аудит | TTL и снятие аренды при падении вкладки, ожидание, простои | **Только как дополнение** |
| Ревизии + оптимистичные конфликты (как сейчас) | Запись с `X-Skyfraze-Base-Revision`, 409 при расхождении (`store.go:611-639`) | Защита от «последний писатель затирает всех» | 409 при каждом параллельном писателе, ретраи, весь снапшот на запись | Да, для аудита и структуры |
| Простые полумеры | Точечные правки без смены модели данных: бэкофф-реконнект, живая модалка, `BroadcastChannel`, ревизия `/tree` | Снимают часть потерь быстро и без миграций | Не решают LWW текста | **Да, делать первыми** (Фаза 0) |

Ключевые выводы по механизмам:

- **CRDT уже выбран и разрешает конфликты на клиенте** — поэтому OT/ShareDB означал бы
  второй механизм конфликтов рядом с первым, переписанный транспорт и два источника правды.
  Смысла нет, пока CRDT не исчерпан.
- **Awareness добавляется в существующий канал**: в hub (`hub.go:328-339`) любой бинарный
  фрейм уже релеится «всем кроме отправителя», а writer всегда шлёт `BinaryMessage`
  (`hub.go:356`). Достаточно различать типы сообщений на клиенте (например, префиксным
  байтом) — серверная логика остаётся релеем, токен и Origin уже проверяются
  (`hub.go:60-104,202-212`). Зависимости уже есть: `yjs`
  (`frontend/package.json:25`), а `y-protocols@1.0.7` и `lib0` лежат в `node_modules`
  как транзитивные.
- **Серверный merge сам по себе текст не спасёт**: пока поля скалярные, слияние всё равно
  LWW. Сначала `Y.Text` (Фаза 2), затем персистенция (Фаза 3).
- **Ревизии полезны там, где они и есть** — структура и аудит; но как основа совместного
  текста они превращают collab в очередь, не решают оффлайн и плодят простои. Ревизия на
  снапшоте конфликтует при каждом параллельном писателе: чем больше участников, тем чаще 409.

### 3.2. Детали по механизмам

**Yjs CRDT (`Y.Text`) + awareness.** Правки становятся последовательностью CRDT-операций:
`Y.Text` вставляет символы с позиционными id, поэтому вставки двух авторов в разных местах
сохраняются обе, а «кто последний» перестаёт быть правилом. Awareness — отдельный, не
сохраняемый в документе канал (курсор, выделение, «печатает…», имя/цвет), который чистится
при отключении. Персистенция — периодическая запись `Y.encodeStateAsUpdate` в
`project_event_state`, а не на каждое нажатие. Платим правкой схемы данных и контролем
размера снапшота; серверный merge в Go — отдельная работа (в репозитории его нет, только
заглушка `hub.go:284-290`). Это минимальное расширение уже выбранного пути.

**Operational Transform (ShareDB/OT-сервер).** Клиент шлёт операции над текстом, сервер
трансформирует их относительно конкурентных и рассылает согласованный порядок; сервер
обязан быть авторитетным и держать документ в памяти. Даёт детерминированный порядок и
серверный авторитет, но требует второго механизма конфликтов, нового обязательного сервиса
и своей OT на Go для структур (перемещение узлов дерева). Для SkyFraze — переусложнение:
CRDT уже стоит и разрешает конфликты без сервера.

**Presence/awareness отдельным каналом.** Поверх уже открытого `/collab` идут короткие
сообщения состояния: кто в проекте, кто на каком событии, курсор/выделение, «печатает…».
Это то, без чего совместная правка ощущается как потерянная, плюс диагностика: сразу видно,
что второй участник оффлайн, а не «сломалось сохранение». Платим фильтрацией типов
сообщений, TTL-очисткой и UI (курсоры, аватары). В hub это ложится без изменений сервера.

**Блокировки/аренда поля.** Поле на время (lease с TTL) принадлежит одному редактору,
остальные видят read-only. Даёт предсказуемость и простой аудит, но «редактирует только
один» плохо переносится на совместную работу: нужны TTL, снятие аренды при падении вкладки
и ожидание освобождения. Годится как точечное дополнение (например, защита фона кадра), не
как основа текста.

**Полумеры.** Дёшево и без смены модели данных: авто-реконнект с бэкоффом и повторной
отправкой состояния, применение чужих правок в открытое модальное окно, `BroadcastChannel`
для вкладок одного пользователя, серверный writer вместо N клиентских, ревизия для
`PUT /events/tree`. Часть потерь снимают сразу, LWW текста ими не лечится.

## 4. Рекомендация: что делать и в каком порядке

Общий принцип: не менять фундамент, а закрыть потери и убрать конкуренцию писателей.
Ниже фазы — каждая маленький проверяемый шаг.

### Фаза 0. Полумеры (без изменения модели данных) — **сделано**

| Шаг | Что сделано | Файлы |
| --- | --- | --- |
| 0.1 | Реконнект с бэкоффом: `backoffDelay(attempt)` 500 мс → 1/2/4/8 с, потолок 15 с, джиттер ±25 %, `createReconnectLoop` с `reset()` при `open` и `stop()` на размонтировании; при `onopen` — досыл `encodeStateAsUpdate` (правки из оффлайна) | `collab/backoff.ts`, `collab/yprovider.ts` |
| 0.2 | Живое модальное окно: политика «что делать с пришедшим текстом» — чистая функция `resolveLiveText({local, base, remote})` → `ignore`/`adopt`/`notify`; черновик не затирается, предупреждение с кнопкой «взять версию соавтора» | `collab/liveText.ts`, `MarkdownEditor.tsx`, `EventEditor.tsx` |
| 0.3 | `BroadcastChannel` на проект: base64-конверт с меткой вкладки, применение чужих апдейтов с origin `'peer'` (обратно не пересылаются — нет эха), тихий откат без `BroadcastChannel` | `collab/broadcast.ts`, `collab/yprovider.ts` |

Запись на уходе больше не гейтится `wsOpened` | `collab/deferredState.ts`, `collab/yprovider.ts` |
| 0.5 | Ревизионная защита `PUT /events/tree`: 428 без `X-Skyfraze-Base-Revision`, 409 + актуальная ревизия при устаревшей базе, проверка в одной транзакции с заменой дерева; клиент при 409/428 перечитывает снапшот, сливает и повторяет проекцию один раз, при 400 — чинит иерархию и повторяет **с** базой | `frontend/src/api/events.ts`, `collab/yprovider.ts`, `events/handler.go`, `events/service.go`, `store/store.go` |

недоступен» — состояние соединения живёт в `collab/connection.ts`
(`connecting`/`open`/`reconnecting`/`offline`), а строка о проекции дерева отделена от
строки о связи.

Проверяемость: два браузера, разрыв сети, две вкладки — см. §5.

### Фаза 1. Presence/awareness на существующем hub — **сделано**

Кто сейчас в проекте, какое событие правит и кто печатает. Сервер не менялся: релей
`hub.go:292-305` пропускает любые кадры, поэтому присутствие едет тем же сокетом.

Как сделано и почему именно так:

- **Свой формат кадра, а не `y-protocols/awareness`.** Хаб — «глупый» релей: он
  рассылает байты всем, кроме отправителя, всегда помечает их binary и при подключении
  сам присылает CRDT-снапшот. Значит, даже со стандартным awareness обрамление кадра
  пришлось бы придумывать самим, а `y-protocols` лежит только транзитивно (объявлять его
  ради одного класса — лишний риск в lockfile). Итог: текстовый префикс `sfp1:` +
  JSON с объявленной длиной, разбор строгий — валидный Yjs-апдейт через него не проходит,
  а разойдись что-то одно, кадр уходит в CRDT как обычно.
- **Три состояния участника**: событие, которое он правит, и «печатает» с коротким
  локальным дебонсом (примерно 1,5 с тишины), чтобы состояние не летело на каждое нажатие.
- **Удаление себя явное** (кадр со `null` при уходе со страницы и размонтировании),
  а призраков снимает таймаут 45 с: три пропущенных удара по 15 с.
- **Вкладки одного человека схлопываются** в одну карточку: в карточке побеждает та
  вкладка, где он печатает.
- **Присутствие не пишется ни в снапшот, ни в базу**: модуль вообще не получает `Y.Doc`,
  поэтому утечь в CRDT ему нечем.

Файлы: `frontend/src/collab/awareness.ts` (+ `awareness.test.ts`), `collab/yprovider.ts`
(кадры поверх сокета, `presence`/`setEditing` в `CollabHandle`), бар присутствия и отметки
в панели редакторов, живая проверка `frontend/tests/presence.ts`.

**Что не вошло и почему.** Посимвольных курсоров («где стоит каретка соавтора») нет:
редактор события — обычный `textarea`, поверх которого каретку соавтора не нарисовать,
а смещение в скалярной строке ничего не значит при одновременном наборе. Смысл у курсоров
появится вместе с `Y.Text` и настоящим текстовым редактором (Фаза 2) — там же, где
посимвольный merge, — и тогда к присутствию добавится только поле «позиция».

### Фаза 2. `Y.Text` для `title`/`body` + миграция старых снапшотов — **сделано**

Посимвольный merge текста: правки двух авторов в одном поле больше не «кто последний,
тот и прав». Файлы: `frontend/src/collab/text.ts` (+ `text.test.ts`), `collab/yprovider.ts`
(миграция при загрузке, проекция, создание событий), `EventEditor.tsx` (правки и фокус),
читающие места (панель, стадия, публичная страница).

Как сделано и почему именно так:

- **Новые ключи `title_text`/`body_text`, старые строки остаются историей.** Переписать
  существующие снапшоты «на сервере» нечем (Yjs на бэкенде нет), поэтому `Y.Text`
  создаётся **лениво из старой строки** — при загрузке проекта одной транзакцией и сразу
  сохраняется. Старая строка больше не пишется и остаётся как есть; читатели ходят через
  `textString`, который умеет оба варианта, поэтому публичная страница и старые данные
  работают без изменений.
- **Гонка двух одновременных миграций безопасна.** На ключе `title_text` окажутся два
  независимых `Y.Text`, LWW выберет один — одинаковый на всех клиентах, а проигравшая
  ветка содержит ту же исходную строку, так что терять в ней нечего. Проверено живым
  тестом: два клиента открывают проект одновременно, текст не удваивается и совпадает.
- **Правка — минимальный диф**, а не перезапись значения: набор в конце даёт одну вставку,
  а не «удалили всё — вставили всё».
- **Чужой текст не стирается никогда.** Если соавтор успел вставить своё, правка человека
  применяется как локальная дельта (`applyLocalEdit`): её индекс сдвигается на чужую
  вставку перед ней, а удаление ограничивается совпадающим куском. Прямой диф «что в поле →
  что в CRDT» в этой ситуации превратил бы чужую вставку в удаление — именно так и терялись
  буквы при одновременном наборе.
- **Пока поле в фокусе, его содержимым владеет человек.** Чужие правки в это поле не
  подставляются: обновлять `value` под руками и восстанавливать каретку можно только
  приблизительно, и ошибка в один символ сдвигала следующую букву (воспроизводилось живым
  набором двух авторов). После потери фокуса поле показывает уже слитый текст, а активность
  соавторов видна в баре присутствия и подписью «печатает…». Плата за это — чужие буквы
  не появляются в поле в момент набора; выигрыш — ни одна буква не теряется и не съезжает.
- Скаляры `event_date`, `assets`, `bg_kind`, `bg_tone`, `bg_asset` остались как есть (§4.1).

Проверка: `frontend/tests/text-merge.ts` — миграция, одновременная миграция двух клиентов,
набор в разных местах (обе правки целиком), одновременный набор в одну позицию (ни один
символ не потерян) и доезд правок до базы через проекцию дерева.

### Фаза 3. Серверный merge и персистенция

Убрать N конкурирующих писателей: снапшот пишет hub (один writer на комнату, редкий
интервал вместо 300 мс на клиента), `persistFromAnyClient` (`hub.go:284-290`) перестаёт
быть заглушкой. Если полноценный merge в Go не поднимается — сохранять «последний снапшот
комнаты» в одном writer'е и оставить клиентский merge только как восстановление. Файлы:
`hub.go`, `service.go`, `store.go`; на клиенте — снять/ослабить `save()`-debounce
(`yprovider.ts:246-254`) и согласовать с `PUT /state`.

### Фаза 4. Проекция дерева из серверного снапшота

После Фазы 3 `PUT /events/tree` от клиента перестаёт быть нужным: сервер сам строит
id/parent_id/position/title/body из сохранённого состояния. До этого — оставить проекцию,
но с ревизией.

### Чего делать НЕ надо

- **OT/ShareDB** — второй механизм конфликтов рядом с CRDT при живом CRDT.
- **Блокировки/аренда поля как основа** — плохой UX и простои; ревизии уже дают нужный
  уровень защиты.
- **Замена транспорта на `y-websocket`** — пакет объявлен (`frontend/package.json:24`), но
  свой hub уже решает токен, Origin и комнаты (`hub.go:60-104`); y-websocket потребует
  переписать auth-слой без выигрыша.
- **Awareness в снапшоте** — присутствие эфемерно; запись его в `project_event_state`
  раздувает снапшот и воскрешает «призраков».
- **Полный переход на серверный merge без Фазы 2** — слияние скаляров всё равно LWW:
  серверный merge сам по себе не спасёт текст.

### 4.1. Что делать с уже существующими скалярными полями

Проблема: `body`/`title` сейчас строки в `Y.Map`, и старые снапшоты в БД содержат именно
строки. Прямая замена `map.set('body', new Y.Text(...))` при одновременном открытии двух
клиентов даёт две конкурирующие `Y.Text` на одном ключе — LWW выберет одну, текст второй
потеряется.

Рекомендуемая схема — **новый ключ + ленивая миграция**:

1. Ввести `body_text` (`Y.Text`), `title_text` (`Y.Text`); старые `body`/`title` остаются
   только для чтения и не перезаписываются.
2. Чтение — один хелпер, например `readText(map, 'body')`: если есть `body_text` — вернуть
   его; иначе взять строку `body` и создать `body_text` в **одной транзакции**
   (`doc.transact`), после чего писать только туда. Так сид из старого снапшота
   (`yprovider.ts:153-162`) и из REST-строк (`listEventRows`) продолжает работать
   без миграции БД.
3. Миграция — ленивая и однократная на проект: победившая `Y.Text` определяется CRDT,
   вторая остаётся пустой веткой и не мешает (её содержимое равно исходной строке).
4. Скаляры `event_date`, `assets`, `bg_kind`, `bg_tone`, `bg_asset` — оставить как есть:
   для даты и фона LWW приемлем, а `assets` при необходимости перевести в `Y.Array`
   отдельным шагом (иначе сохраняется проблема union-семантики, §2.1). Дата при этом уже
   ездит в обе стороны: проекция дерева несёт `event_date` (RFC3339), а засев CRDT из
   таблицы событий — обратно; отсутствие поля в проекции значит «дату не трогать».
5. `PUT /events/tree` продолжает читать `title`/`body` через `yFlatTree`
   (`yprovider.ts:443-458`); после Фазы 2 её надо переключить на `readText`, иначе проекция
   перестанет видеть правки. Совместимость со старыми снапшотами при этом сохраняется:
   `Y.applyUpdate` старого состояния даёт тот же `Y.Map` со строковыми ключами.

Миграцию БД (`project_event_state`) делать не нужно — снапшот остаётся одним BYTEA
(`0002_events_hierarchy.up.sql:52-58`), меняется только форма содержимого.

## 5. Риски и как их проверять

Автоматически проверяются на поднятом стенде:
`npx tsx tests/realtime-phase0.ts` (вкладка без realtime, две вкладки одного браузера,
обрыв сокета, устаревшая ревизия снапшота) и
`npx tsx tests/presence.ts` (два человека в двух браузерных контекстах: видят друг
друга через сервер, «печатает…» появляется и гаснет, уход убирает карточку).

| Риск | Как проверять |
| --- | --- |
| Потеря текста при одновременном наборе | Два браузера, оба печатают в `body` одного события; после обоих сохранений текст содержит оба фрагмента *(остаётся: Фаза 2)* |
| Правки не доезжают при обрыве сети | Отключить сеть у одного клиента, печатать, вернуть сеть: после реконнекта апдейт уходит (Фаза 0.1) и виден второму — покрыто `tests/realtime-phase0.ts` |
| Модальное окно затирает чужое | Открыть Markdown-редактор у A, править `body` у B, «Сохранить» у A: текст B сохраняется (политика — `collab/liveText.ts`) |
| Гонка ревизий при N писателях | 20 одновременных правок: считать 409 и 500 в логах бэкенда; после Фазы 3 409 должны исчезнуть |
| `PUT /events/tree` сносит чужие строки | Устаревший клиент (оффлайн с момента до правок B) делает проекцию: строки B остаются (ревизия отклоняет замену) — покрыто `tests/realtime-phase0.ts` |
| Проекция не уходит от клиента без realtime | Вкладка с закрытым сокетом добавляет главу: событие появляется в `GET /events` — покрыто `tests/realtime-phase0.ts` |
| Закрытие вкладки теряет последнюю правку | Править и сразу закрыть вкладку, затем проверить состояние в другом браузере; при конфликте — повтор при следующем открытии (запас в `localStorage`) |
| Awareness мусорит или мешает CRDT | Отключение клиента без close-фрейма: карточка исчезает по таймауту, документ не меняется — покрыто `tests/presence.ts` |
| Присутствие протекает в данные проекта | В дереве событий и в снапшоте нет ни имён, ни полей присутствия — проверяет `tests/presence.ts` |
| Две вкладки одного пользователя | Править в обеих: состояния сходятся без перезагрузки — покрыто `tests/realtime-phase0.ts` |
| Разрастание снапшота и БД | Замер `length(yjs_state)` до/после сессии, число записей `revision` за час |
