# DOCX по шаблону автора — проработка (0.91+)

Статус: **проработка идеи, код не начат.** Документ отвечает на вопрос «как сделать так, чтобы
проект скачивался в DOCX в оформлении автора», и заранее разбирает места, где это задевает поиск,
отображение Markdown и ИИ-помощника.

## 1. Как сейчас (и почему этого мало)

Файл `backend/internal/transfer/export_docx.go` собирает DOCX **с нуля**: свой zip, свой
`word/document.xml`, свои `word/styles.xml`. Стили жёстко заданы в константе `docxStyles`:
`Title`, `Heading1…3`, `Quote`, `Code`, `Date`, `ListNested`, `TableHead`, шрифт Georgia 12 pt,
поля страницы 2 см. Заголовки кадра выбираются по глубине (`depth`), остальное — телом.

Что уже есть и пригодится:

* разметка кадров разбирается **одним** кодом для EPUB и DOCX (`markdown_html.go`: `parseMarkdown`,
  `inlineRuns`) — оформление разное, трактовка текста общая;
* картинки кадра вставляются встроенными объектами (`docxImage`), с ограничением 6 дюймов по ширине;
* ограничения честно записаны в `docs/import-export.md`: таблицы — простой сеткой строк, вложенные
  списки — не глубже второго уровня.

Чего нет: автор не может задать **своё** оформление. Человеку, который отдаёт рукопись в
издательство, нужен файл со своими стилями, колонтитулами, титулом и полями — иначе он получает
«файл из программы», а потом переоформляет вручную.

## 2. Два способа «взять оформление из docx»

### Вариант A. Прочитать стили шаблона и собрать документ своим пакетом

Разбираем `word/styles.xml` шаблона, берём `styleId`/имена/размеры, подставляем в наш генератор.

* **Плюс:** просто; наш код остаётся хозяином пакета, никакой чужой XML не переносим.
* **Минус:** теряется всё, кроме шрифтов и стилей абзацев: титульная страница, колонтитулы, номера
  страниц, поля и размер страницы, тема, нумерация списков, табличные стили. То есть «оформление»
  берётся частично — и человек всё равно видит не свой шаблон.

### Вариант B. Шаблон как основа пакета, наш текст вставляется в него

Берём zip шаблона целиком и **заменяем плейсхолдер** нашим содержимым:

* в шаблоне есть абзац с текстом `{{content}}` (или абзац со стилем с именем `SkyFraze Content`);
* всё остальное остаётся автора: титул, раздел, колонтитулы, поля, нумерация страниц, тема,
  стили, numbering.

* **Плюс:** человек получает ровно свой документ, а не «похожий».
* **Минус:** мы обязаны аккуратно дописывать части пакета (картинки, связи), не ломая чужие; и
  должны определить, какими стилями набирать заголовки и текст — по именам стилей шаблона и по
  свойствам абзаца-плейсхолдера.

**Рекомендация: B.** Именно он отвечает на запрос «проект оборачивается в готовый файл docx нужного
вида». A остаётся запасным путём, когда шаблон не даёт плейсхолдера (см. §4.4).

### 2.1. Как понять, каким стилем что набирать

При загрузке шаблона строим **карту сопоставления** и показываем её человеку:

| Что в проекте | Ищем в шаблоне | Если нет |
|---|---|---|
| название проекта | стиль `Title` (по `w:styleId` или `w:name` = «title»), иначе первый абзац с крупным шрифтом | встроенный `Title` |
| глава (depth 0) | `Heading1` / «heading 1» | ближайший существующий `HeadingN`, ниже — `Title` |
| под-событие (depth 1) | `Heading2` | `Heading1` |
| под-под (depth 2+) | `Heading3`/`Heading4` | последний найденный `HeadingN` |
| обычный текст | **свойства абзаца-плейсхолдера** (`pPr`: шрифт, отступ, интервал) | `Normal` шаблона |
| цитата | `Quote` | встроенный `Quote` |
| код | `Code` / `Source Code` | встроенный `Code` |
| список | `ListParagraph` + `numId` из `numbering.xml`, если есть | маркеры «•»/«1.» как сейчас |
| дата кадра | `Date` | встроенный `Date` |

Отчёт загрузки показывает карту и **что не сработало** («стиля Heading 2 в шаблоне нет — использую
Heading 1»). Молча подменять оформление нельзя: человек должен видеть, где шаблон не совпал с
ожиданием.

## 3. Маркеры в тексте

Markdown не выражает того, что умеет DOCX: разрыв страницы, «этот блок — стихом», «здесь
оглавление», «этот абзац — эпиграф из шаблона». Поэтому — **маркеры в тексте кадра**.

### 3.1. Синтаксис: HTML-комментарии

```markdown
<!-- sf:pagebreak -->

<!-- sf:style=Эпиграф -->
Так начинается ночь…

<!-- sf:toc -->
```

Почему комментарии:

* это **стандартный Markdown**, его понимают все редакторы и хранилища; ничего не ломается при
  копировании и экспорте `.md` (маркеры остаются в исходнике — обратный импорт их сохранит);
* в отображении их **нет**, если их вырезать (см. §3.3) — «игнорируются разметкой», как и просили;
* ИИ-помощник читает и пишет их как обычный текст, без отдельного протокола;
* `-->` невозможно внутри комментария — граница маркера однозначна.

Правила разбора:

* маркер — только **отдельной строкой** (или в строке целиком), начинается с `<!-- sf:` и
  заканчивается `-->` на той же строке; всё прочее, похожее на комментарий, — обычный текст;
* внутри ``` ``` ``` -блоков (код, mermaid) маркеры **не разбираются** — это код, а не разметка;
* неизвестная команда или неизвестный стиль — **пропуск команды** + предупреждение в отчёте
  выгрузки; текст при этом не теряется.

### 3.2. Словарь v1 (закрытый)

| Маркер | Что делает в DOCX | В EPUB / показе |
|---|---|---|
| `<!-- sf:pagebreak -->` | разрыв страницы | игнорируется (в EPUB — новый раздел? нет, просто пропуск) |
| `<!-- sf:toc -->` | поле оглавления Word (`TOC \o "1-3"`), обновится при открытии | пропуск |
| `<!-- sf:style=Имя -->` | следующий блок — стилем «Имя» из шаблона | пропуск |
| `<!-- sf:begin=Имя -->` … `<!-- sf:end -->` | блок целиком — стилем «Имя» | пропуск |

Больше в v1 не берём: каждая команда — это ветка рендера и тесты. Расширять после того, как эти
четыре проверятся на реальных рукописях.

### 3.3. Где маркеры надо вырезать (и где нельзя)

Ключевое требование: **невидимы в показе, не участвуют в поиске, но не сдвигают позиции** —
упоминания карточек и якоря замечаний хранят `from`/`to` в UTF-16 по сырому тексту.

Приём один: **маскировка с сохранением длины** — символы маркера заменяются на `\u0000`
(не совпадает ни с чем и не рисуется), длина строки не меняется. Так:

* поиск и упоминания работают по маскированной строке, а найденные `from`/`to` остаются валидными
  для сырого текста;
* сниппет берётся из сырого текста, но маркеры в нём заменены на пробелы;
* показ — по маскированной строке (после маскировки в ней нет `<`, так что `html: false` в
  markdown-it не превратит маркер в видимый текст).

Точки, которые обязаны знать о маркерах (проверять каждую):

| Место | Файл | Что делать | Тест |
|---|---|---|---|
| показ Markdown в карточке/публичной истории | `frontend/src/lib/markdown.ts` | маскировать до markdown-it | в HTML нет `<!-- sf:` и нет `sf:` |
| поиск по проекту | `frontend/src/lib/projectSearch.ts` | искать по маске, сниппет — из маски | ищется слово, не ищется текст маркера; сниппет чистый |
| упоминания карточек | `frontend/src/collab/mentions.ts` (`findMentions`, `frameMentions`) | маска до поиска | `from`/`to` совпадают с сырым текстом; в маркере не находится имя |
| объём кадра (длина прокрутки) | `frontend/src/components/timeline/timelineModel.ts` (`textUnits`) | считать по маске | маркер не удлиняет кадр |
| вес проекта в списке | `frontend/src/lib/projectWeight.ts` | по маске | не влияет |
| серверный разбор (EPUB) | `backend/internal/transfer/markdown_html.go` (`parseMarkdown`) | строки-маркеры пропускать | EPUB без `sf:` |
| серверный разбор (DOCX) | там же, но до `parseMarkdown` | маркеры **читать** и применять | стиль/разрыв на месте |
| выгрузка `.md` и `story.md` | `markdown.go` | **оставить как есть** | обратный импорт сохраняет маркеры |

Последняя строка — важная: `.md` — это исходник, и вычищать из него маркеры значило бы терять
разметку при экспорте-импорте. Маркеры вырезаются только там, где текст *показывается*.

### 3.4. Интерфейс

В редакторе кадра — раскрывающаяся панель **«Разметка DOCX»**:

* список доступных команд (разрыв, оглавление) и **стилей из загруженного шаблона** (человек
  выбирает из того, что реально есть, а не пишет имя по памяти);
* кнопка вставляет маркер в позицию курсора (тот же приём, что вставка `@упоминания`);
* подсказка: «в показе проекта маркер не виден, он действует только при скачивании в DOCX»;
* если шаблон не загружен — панель говорит об этом и предлагает загрузить (без шаблона маркеры
  стилей работать не будут, но `pagebreak`/`toc` — будут).

## 4. Хранение и API

### 4.1. Миграция `0036_project_docx_templates`

Одна настройка на проект (v1 — один шаблон):

```sql
CREATE TABLE IF NOT EXISTS project_docx_templates (
  project_id  uuid PRIMARY KEY REFERENCES projects(id) ON DELETE CASCADE,
  asset_id    uuid NOT NULL,              -- файл в хранилище (не обычное вложение кадра)
  filename    text NOT NULL,
  size        bigint NOT NULL,
  styles      jsonb NOT NULL DEFAULT '[]',-- [{id,name,type,builtin}]
  placeholder jsonb NOT NULL DEFAULT '{}',-- {found, paragraph_style_id, body_pPr_xml?}
  page        jsonb NOT NULL DEFAULT '{}',-- {width,twips,height,orientation,margins}
  report      jsonb NOT NULL DEFAULT '{}',-- отчёт загрузки и карта стилей
  uploaded_by uuid REFERENCES users(id),
  uploaded_at timestamptz NOT NULL DEFAULT now()
);
```

Почему отдельная таблица, а не поле в `project_ai_settings`: шаблон — это файл и результат разбора,
и он живёт по своим правилам (лимиты, отчёт, замена). В `assets` файл не кладём как вложение:
вложения входят в архив и в список файлов проекта — шаблон оформления туда не относится.

### 4.2. Ручки (в под-дереве `/api/projects/{id}`)

| Метод | Путь | Права | Что делает |
|---|---|---|---|
| `POST` | `/docx-template` | владелец | multipart `.docx` ≤ 20 МБ; разбор и отчёт; старый шаблон заменяется |
| `GET` | `/docx-template` | редактор+ | метаданные и отчёт (для панели «Разметка DOCX») |
| `DELETE` | `/docx-template` | владелец | убрать шаблон (выгрузка вернётся к встроенному оформлению) |

Выгрузка `GET /export/docx` сама берёт шаблон, если он есть. В ответ добавляется заголовок
`X-SkyFraze-Docx-Template: custom|builtin`, чтобы интерфейс мог сказать, каким оформлением собран
файл (тело — сам DOCX, отчёт туда не влезет).

### 4.3. Разбор шаблона при загрузке

1. Проверить, что это zip и `.docx` (не `.docm`): есть `[Content_Types].xml`, `word/document.xml`.
2. Лимиты: размер ≤ 20 МБ, частей ≤ 800, распакованный объём ≤ 200 МБ (те же страхи, что у архива).
3. `word/styles.xml` → список стилей абзацев: `styleId`, `w:name`, `w:basedOn`, `w:type`,
   признак `w:builtin`.
4. `word/document.xml` → найти плейсхолдер:
   * первый абзац, текст которого ровно `{{content}}`;
   * иначе первый абзац со стилем, имя которого содержит `skytraze content` / `skytraze`;
   * иначе — **шаблон без плейсхолдера** (см. §4.4).
5. Запомнить `pPr` абзаца-плейсхолдера — это оформление обычного текста (шрифт, отступ, интервал).
6. `sectPr` → размер страницы, ориентация, поля (только для отчёта; сам шаблон их уже содержит).
7. `word/numbering.xml` → есть ли нумерованные списки (для отчёта «списки будут с маркерами»).

### 4.4. Выгрузка: как вставляется текст

1. Открыть zip шаблона, прочитать `word/document.xml`.
2. Разрезать `w:body` на «до плейсхолдера» и «после», сам абзац-плейсхолдер выбросить.
3. Сгенерировать XML содержимого: каждый кадр — заголовок нужным стилем + дата + картинки + блоки
   `parseMarkdown`; маркеры применены (разрыв страницы, стиль, оглавление).
4. Вставить сгенерированное между «до» и «после»; `sectPr` остаётся последним элементом `w:body`.
5. Картинки: дописать `word/media/*`, связи в `word/_rels/document.xml.rels` с **свободными** `rId`
   (в шаблоне они уже заняты), `Default` для расширений в `[Content_Types].xml` (если нет).
6. Записать пакет заново. Все прочие части шаблона копируются байт-в-байт.

**Если плейсхолдера нет:** загрузка **отказывает** с объяснением («в шаблоне нет абзаца
{{content}} — добавьте его отдельной строкой»). Так решили при реализации 0.91.0: шаблон без
плейсхолдера бесполезен (вставлять некуда, а стили применить к нашему собственному пакету нельзя),
и «загрузилось, но скачивание не изменилось» — худший исход. Вариант «дописать в конец» не
делаем: на титуле оказывается текст рукописи.

### 4.5. Ограничения DOCX, о которых надо сказать в интерфейсе

* Стили Word ссылаются на **шрифты по имени**; если у читателя шрифта нет — Word подставит свой.
  Встраивание шрифтов (`w:embedTrueTypeFonts`) не делаем: вес файла и лицензии.
* Оглавление — поле: Word спросит «обновить поля» при открытии. Это нормально и ожидаемо.
* Колонки, текстовые поля, фигуры, надписи из шаблона **не переносим внутрь тела** — они
  остаются на своих местах (титул, колонтитулы), но наш текст их не обтекает.
* Таблицы Markdown — простые; в шаблонных табличных стилях останутся границы по умолчанию.

## 5. ИИ-помощник и маркеры

Помощник пишет текст кадров тем же полем, что и человек, поэтому:

1. В подсказку модели добавляется компактный список: допустимые маркеры, **имена стилей из
   шаблона проекта** (их немного), правило «маркеры — отдельной строкой, не трогай чужие».
2. При применении правки (путь `assistant` → тот же редактор кадров) — валидация: неизвестный
   маркер не ломает текст, но попадает в предупреждение; известный — сохраняется.
3. Помощник не должен «съедать» маркеры при переписывании абзаца: правки применяются по фрагменту,
   а маркер, стоящий отдельной строкой, в фрагмент не попадает — это надо закрепить тестом.
4. Если шаблон не загружен, помощник видит только `pagebreak`/`toc` (они не требуют стилей).

## 6. Что именно задевает поиск и отображение (сводка рисков)

| Риск | Почему опасен | Как закрываем |
|---|---|---|
| маркер виден в публичной истории | «<!-- sf:pagebreak -->» в тексте выглядит как поломка | маска до markdown-it + тест рендера |
| упоминания сдвигаются | `from`/`to` считаются по сырому тексту; если вырезать маркер, сместятся все якоря замечаний | маскировка **с сохранением длины** |
| поиск находит служебные слова (`sf`, `style`, имя стиля) | ложные попадания | поиск по маске |
| маркер внутри ``` ``` | `-->` и `<` в коде нельзя трогать | разбор учитывает fenced-блоки |
| длинный маркер удлиняет кадр в прокрутке | вес кадра считается по `textUnits` | считать по маске |
| `.md`-экспорт теряет разметку | вычистили при выгрузке | в `.md`/`story.md` маркеры остаются |
| шаблон с макросами (.docm) | исполняемый контент | отклоняем по MIME/частям пакета |
| zip-бомба | сервер | лимиты размера/частей/распаковки |
| XML шаблона с внешними сущностями | SSRF/файлы | Go `encoding/xml` не резолвит внешние сущности; текст экранируем; `altChunk` не поддерживаем |

## 8. Чего сознательно не делаем

* не поддерживаем `.doc`, `.docm`, RTF и «любой docx как движок вёрстки» (текстовые поля, фигуры,
  SmartArt, колонки, сноски, перекрёстные ссылки);
* не делаем двустороннюю синхронизацию «правки в Word → проект»;
* не встраиваем шрифты в файл;
* не обновляем поля оглавления сами (это делает Word при открытии);
* не распознаём картинки/лица (это отдельная фича из §3.4.1 `docs/entity-links.md`).

1. **Плейсхолдер** `{{content}}` отдельным абзацем — да. Без него загрузка отказывает (см. §4.4).

3. **Шаблонов несколько, именованных** — да, чтобы переключаться («рукопись», «самиздат»).
