## Быстрый старт через Docker (production-like)

```bash
# 1. Клонировать вместе с сабмодулем: в deps/scroll-world лежит референс движка
#    прокрутки (используется как справочник по композиции, не импортируется в сборку)
git clone --recurse-submodules https://github.com/BarsSky/SkyFraze.git
cd SkyFraze

# 2. Скопировать env-шаблон и заполнить JWT_SECRET
cp .env.example .env
# (на dev можно оставить дефолт, но обязательно 32+ байта в проде)

# 3. Собрать и поднять весь стек
docker compose up --build -d

# 4. Открыть UI
open http://localhost      # macOS
# или xdg-open http://localhost / просто ввести в браузере
```

Если репозиторий уже склонирован без сабмодулей: `git submodule update --init --recursive`.

После `docker compose up`:
- **Frontend** (UI + nginx proxy): http://localhost (port 80)
- **Backend** (Go API): internal :8080 (доступен только через nginx)
- **Postgres**: localhost:5432 (`skyfraze` / `skyfraze_dev` — для локальной отладки)

Health-check:
```bash
docker compose ps            # все 3 сервиса должны быть healthy
curl http://localhost/api/health   # {"status":"ok"}
```

Остановка:
```bash
docker compose down          # остановить
docker compose down -v       # остановить и удалить volumes (ПОТЕРЯ ДАННЫХ)
```

## Запуск без Docker (dev-режим)

```bash
# Postgres (через docker)
docker compose up postgres -d

# Backend
cd backend
export DATABASE_URL="postgres://skyfraze:skyfraze_dev@localhost:5432/skyfraze?sslmode=disable"
export JWT_SECRET="dev-secret"
export CORS_ORIGINS="http://localhost:5173"
export STORAGE_DIR="./storage"
go run ./cmd/server

# Frontend (в другом терминале)
cd frontend
npm install
npm run dev   # Vite поднимет на http://localhost:5173
```

## Администрирование и режим регистрации

По умолчанию инсталляция **закрыта**: зарегистрироваться самому нельзя, доступ выдаётся
по заявке. Открытая регистрация — осознанное решение администратора.

### Что задаётся при развёртывании

```bash
# .env (см. .env.example)
ADMIN_EMAILS=you@example.com          # администраторы (через запятую)
REGISTRATION_MODE=request             # request (по заявке, дефолт) | open (свободная)
```

| Переменная | Смысл |
|---|---|
| `ADMIN_EMAILS` | Кто администратор. Права выдаются уже зарегистрированным **и** тем, кто зарегистрируется позже (проверка при входе). Список пуст → администратором становится первый зарегистрированный пользователь (в логе будет предупреждение) |
| `REGISTRATION_MODE` | Стартовый режим, пока администратор не поменял его в интерфейсе. После первого решения админа значение из env больше не применяется — иначе развёртывание перебивало бы решение человека |

### Что делает администратор

`/admin` (ссылка появляется в шапке у администратора):

- переключает режим: **«По заявке»** ↔ **«Свободная»**;
- видит заявки (на рассмотрении / одобренные / отклонённые), одобряет и отклоняет их;
- видит список пользователей инсталляции.

Администратор **не получает доступа к содержимому чужих проектов** — его зона только
вход на инсталляцию.

### Как работает заявка

1. Человек заполняет форму на `/register`: имя, email, **пароль** и зачем ему доступ.
2. Пароль сразу сохраняется хэшем, аккаунт не создаётся — заявка получает статус `pending`.
3. До решения вход даёт понятное `403`: «заявка ещё не одобрена» (заявку можно найти по
   email и паролю, поэтому посторонний по одному email ничего не узнает).
4. Администратор одобряет — аккаунт создаётся, человек входит **тем паролем, который
   указал при подаче** (почтовых ссылок не требуется). Отклонённая заявка объясняет отказ.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/auth/config` | аноним | текущий режим регистрации для формы |
| POST | `/api/auth/registration-requests` | аноним | подать заявку (202) |
| GET | `/api/admin/settings` | админ | режим, счётчики |
| PATCH | `/api/admin/settings` | админ | `{"registration_mode":"request"\|"open"}` |
| GET | `/api/admin/registrations?status=pending` | админ | список заявок |
| POST | `/api/admin/registrations/{id}/approve` \| `/reject` | админ | решение |
| GET | `/api/admin/users` | админ | пользователи инсталляции |

## Публичная лента

Проект попадает в ленту **только после явного действия владельца**: в списке проектов
кнопка «Опубликовать». До этого он не виден никому, кроме команды, — в том числе по ссылке.

```bash
# публикация / снятие (только владелец проекта)
curl -X POST http://localhost/api/projects/<id>/publication \
  -H "Authorization: Bearer <access>" -H 'Content-Type: application/json' \
  -d '{"is_public":true}'

# лента и публичная история — без авторизации
curl http://localhost/api/public/feed?sort=new
curl http://localhost/api/public/stories/<slug>
```

| Что | Как |
|---|---|
| Лента | `GET /api/public/feed?sort=new\|rating\|views` |
| История | `GET /api/public/stories/{slug}` (+1 просмотр, дедуп по cookie `sf_vid`) |
| Оценка | `POST /api/public/stories/{slug}/rating` `{"stars":1..5}` (нужен вход) |
| Снять оценку | `DELETE /api/public/stories/{slug}/rating` |
| Публичные файлы | `GET /api/public/assets/{id}` — только для опубликованных проектов |
| Публикация | `POST /api/projects/{id}/publication` — только владелец |

Ограничения, заложенные в модель: по умолчанию всё закрыто; снятие с публикации
закрывает и историю, и её файлы (404); ссылка `slug` не меняется между публикациями;
публичные ручки не содержат ни одной операции записи в содержимое истории.

## Корзина проектов

Удаление проекта **не стирает рукопись**. Кнопка «Удалить» отправляет проект в корзину, где
он лежит 30 дней: за это время его можно вернуть со всем содержимым, а по истечении срока
его окончательно убирает фоновая уборка (тот же процесс, что чистит осиротевшие файлы).

Что важно знать:

- пока проект в корзине, он **не виден никому** — ни владельцу в списке, ни команде по
  прямой ссылке, ни читателям в публичной ленте. «Удалил» не значит «спрятал от себя,
  оставил соавторам»;
- **вернуть может только владелец**: корзина — личное хозяйство, а не общая папка отходов;
- возврат **полный**: события, вложения и история версий не удалялись, а файлы в хранилище
  остаются на месте до окончательного удаления;
- «Удалить навсегда» — **отдельная кнопка** и только для проекта из корзины: необратимое
  действие не должно делаться тем же нажатием, что обратимое. Файлы уходят вместе с
  проектом (если на них не ссылается другой проект — вложения дедуплицируются);
- в корзине видно **вес файлов** проекта (сколько места освободится) и кнопку **«Скачать
  архив»**: сохранить проект перед необратимым удалением можно, не возвращая его в список —
  «удалить можно, а посмотреть нельзя» не порядок. Право то же, что на возврат: только
  владелец;
- срок хранения — одна константа на сервер, интерфейс и уборку (`projects.TrashRetention`),
  чтобы «30 дней» не разошлись между тремя местами.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/projects/trash` | вход | удалённые проекты: `id`, `title`, `description`, `deleted_at`, `days_left`, `asset_bytes` и `retention_days` |
| GET | `/api/projects/{id}/export` | владелец корзины | архив проекта, в том числе из корзины (не возвращая в список) |
| DELETE | `/api/projects/{id}` | владелец | в корзину (повторное нажатие — не ошибка) |
| POST | `/api/projects/{id}/restore` | владелец | вернуть из корзины (204) |
| DELETE | `/api/projects/{id}/purge` | владелец | удалить навсегда, только из корзины (204; активный проект — 404) |

```bash
# что лежит в корзине и сколько ещё можно вернуть
curl -H "Authorization: Bearer <access>" http://localhost/api/projects/trash

# вернуть
curl -X POST -H "Authorization: Bearer <access>" \
     http://localhost/api/projects/<id>/restore

# удалить окончательно
curl -X DELETE -H "Authorization: Bearer <access>" \
     http://localhost/api/projects/<id>/purge
```

## Ошибки в интерфейсе

Сырых исключений в UI нет: любая ошибка загрузки показывается **плашкой** с объяснением
по-человечески, кнопкой «Повторить» (для временных сбоев) и ссылкой на доступную
страницу — «← В ленту», «Мои проекты», «К проектам». Классификация ошибок —
`frontend/src/lib/apiError.ts` (нет связи / таймаут / 5xx / 401 / 403 / 404 / 409),
компонент — `frontend/src/components/ErrorBanner.tsx`.

Публичные запросы повторяются автоматически (`retry` в `src/api/feed.ts`), история
получает увеличенный таймаут: ответ несёт CRDT-снапшот, а перезапуск контейнера на
несколько секунд рвёт соединение.

## Перенос проекта между стендами

Проект можно целиком перевезти с одного SkyFraze на другой: в списке проектов кнопка
**«Экспорт»** скачивает архив `*.skyfraze.zip`, а кнопка **«Импорт проекта»** на другом
стенде создаёт из него новый проект. В архив попадает всё содержимое:

| Что внутри | Зачем |
|---|---|
| `manifest.json` | формат, версия, название/описание, дерево событий (id, parent_id, position, depth, title, body, event_date), список вложений |
| `state.bin` | CRDT-снапшот: тексты кадров, фон (тон/картинка), привязки вложений — то, чего нет в реляционной модели |
| `assets/<id>` | сами файлы вложений (картинки, PDF, аудио) |

```bash
# скачать архив (нужен токен: это приватный проект)
curl -H "Authorization: Bearer <access>" -OJ http://localhost/api/projects/<id>/export

# загрузить на другом стенде — создастся новый проект у того, кто загрузил
curl -H "Authorization: Bearer <access>" -F "file=@project.skyfraze.zip" \
     http://other-host/api/projects/import
```

Что важно знать:

- **импорт всегда создаёт новый проект** у загрузившего (владельцем становится он), и
  никогда не пишет в существующий;
- **идентификаторы событий и вложений сохраняются как есть** — на них ссылается
  CRDT-снапшот, а переписать бинарный Yjs-update без парсера Yjs нельзя. Поэтому
  повторная загрузка того же архива в ту же базу распознаётся и отклоняется (`409`
  «этот архив уже импортирован»): удалите ранее импортированный проект или грузите на
  другом стенде;
- переносятся только содержимое проекта. Просмотры, оценки и публикация — это свойства
  инсталляции, а не проекта: на новом стенде проект приезжает **закрытым**;
- лимиты: архив до 200 МБ, один файл до 50 МБ, до 5000 событий и 500 вложений
  (nginx пускает 256 МБ — см. `frontend/nginx.conf`);
- экспорт доступен роли `viewer` и выше (читатель и так видит всё содержимое проекта),
  импорт — любому вошедшему.

Проект, у которого нет CRDT-снапшота (создан через API или приехал из такого архива),
при первом открытии в редакторе засевается из реляционного дерева — иначе стадия
считала бы его пустым.

## Развёртывание на сервере

Для сервера есть отдельный compose-файл — он не публикует Postgres наружу и позволяет
задать порт UI:

```bash
# на сервере, в каталоге проекта
cat > .env <<EOF
JWT_SECRET=$(openssl rand -hex 32)
ADMIN_EMAILS=you@example.com      # администратор(ы) инсталляции
REGISTRATION_MODE=request         # по заявке (дефолт) | open
SKYFRAZE_PORT=80                  # порт, на котором открыт UI
CORS_ORIGINS=http://<адрес-хоста>
EOF

docker compose -f docker-compose.prod.yml up -d --build
```

Почему отдельный файл, а не `docker-compose.yml`: dev-версия публикует `5432:5432`, и на
сервере, где уже есть системный Postgres (или mailcow), контейнер просто не поднимется
из-за занятого порта. Для сервера база доступна только backend'у по внутренней сети.

### Первый вход: как появляется администратор

Инсталляция закрыта по умолчанию: чужие регистрируются только по заявке. Чтобы это не
заблокировало развёртывание, прямая регистрация разрешена в трёх случаях:

1. режим `open` — администратор так решил;
2. **инсталляция пустая** — тот, кто зарегистрировался первым, создаёт её и становится
   администратором (на странице регистрации так и написано: «Первый администратор»);
3. email входит в `ADMIN_EMAILS` — администратор, назначенный развёртыванием, заводит
   себе аккаунт независимо от режима и сразу получает права.

Дальше все остальные проходят через заявку: `POST /api/auth/registration-requests`,
решение — в `/admin`. Полный порядок работы с режимом и заявками — в разделе
«Администрирование и режим регистрации».

### Управление развёрнутым стендом

```bash
cd /path/to/skyfraze
docker compose -f docker-compose.prod.yml ps        # статус
docker compose -f docker-compose.prod.yml logs -f backend
docker compose -f docker-compose.prod.yml up -d --build   # обновление после копирования новой версии
docker compose -f docker-compose.prod.yml down      # остановить (данные в volumes остаются)
```

Проверка, что стенд жив (можно запускать с любой машины, где есть Node):

```bash
cd frontend && DEPLOY_URL=http://192.168.13.66 npx tsx tests/deployed-smoke.ts

# Проверка мобильного сценария на развёрнутом стенде (незащищённый контекст,
# создание событий, кнопки меню и редакторов). Требует временного пользователя:
# на стенде временно включается открытая регистрация, затем пользователь удаляется.
cd frontend && REMOTE_URL=http://192.168.13.66 TEMP_EMAIL=you@example.com npx tsx tests/remote-mobile-check.ts
```

**HTTPS-сценарий локально** (`deploy/tls-proxy/Caddyfile`): тот же `remote-mobile-check.ts`
против `https://fraza.localtest.me:8443`. Нужен потому, что на `localhost` браузер считает
контекст доверенным и не блокирует `ws://` со страницы `http(s)://localhost` — дефект
«realtime молчит, потому что страница по HTTPS» там просто не воспроизводится. Команды
запуска — в комментариях внутри `Caddyfile` (`tls internal`, WebSocket без доработок,
`docker network connect skyfraze_skyfraze-net sf-tls`).

### Обновление стенда из GitHub

Раздел **«Обновление»** в `/admin` показывает текущую версию и последний релиз репозитория,
умеет проверять обновления и оставлять заявку на применение.

Как это устроено (и почему не «кнопка с docker.sock»):

```
админка  ──POST /api/admin/update──►  update-state/request.json   (общий каталог с хостом)
                                              │
systemd skyfraze-update.path замечает файл ───┘
        │
        └─► deploy/skyfraze-update.sh: git fetch → checkout тега → docker compose up -d --build
                     │
                     └─► update-state/status.json + update.log ──► админка показывает прогресс
```

Приложение работает в контейнере, а исходники и compose — на хосте, поэтому пересборку
делает хост: веб-процессу не нужен `docker.sock` (это был бы root на хосте).

```bash
# 1. Источник релизов (в .env на сервере)
UPDATE_REPO=BarsSky/SkyFraze     # owner/name; пусто → раздел скажет, что источник не настроен
# UPDATE_TOKEN=...               # только для приватного репозитория / лимитов API
UPDATE_CHANNEL=stable            # stable игнорирует предрелизы

# 2. Применятель: скрипт + systemd-юниты (один раз, на хосте)
sudo bash deploy/install-update-units.sh /путь/к/проекту

# 3. Проверить вручную, не дожидаясь админки
sudo deploy/skyfraze-update.sh            # до последнего тега
sudo deploy/skyfraze-update.sh v0.2.1     # до конкретной версии
tail -f update-state/update.log
```

Требование к установке: каталог проекта должен быть **git-клоном** (`.env` и `update-state/`
в `.gitignore`, поэтому обновление их не трогает). Если стенд разворачивался копированием
файлов — один раз инициализируйте репозиторий:

```bash
cd /путь/к/проекту
git init -b master && git remote add origin https://github.com/BarsSky/SkyFraze.git
git fetch --tags origin && git checkout -f -B master origin/master
```

## Структура репозитория

```
SkyFraze/
├── backend/                      Go API
│   ├── cmd/server/               main.go
│   ├── internal/
│   │   ├── auth/                 JWT, register/login/refresh, режим регистрации, заявки
│   │   ├── users/                профиль, ники, резюме и специализации резидентов
│   │   ├── admin/                админка развёртывания: настройки и заявки
│   │   ├── update/               механизм обновления стенда из GitHub
│   │   ├── projects/             CRUD + ownership
│   │   ├── projecttemplate/      шаблон проекта: типы, карточки, настройки помощника
│   │   ├── teams/                invitations, roles
│   │   ├── coauthors/            творческий круг: заявки, специализации, доступ на чтение
│   │   ├── people/               каталог резидентов
│   │   ├── feed/                 публичная лента: публикация, просмотры, оценки
```

Ключи стенда к размещённым провайдерам нужны, только если вы сами оплачиваете модель
для всех: `GROQ_API_KEY`, `OPENROUTER_API_KEY`, `GOOGLE_API_KEY`, `OPENAI_API_KEY`,
`CUSTOM_AI_API_KEY` (для своего шлюза из `AI_OPENAI_COMPAT_URL`). Без них работает
локальная модель и ключи самих пользователей — ключ пользователя приоритетнее ключа
стенда. Задаются в `.env` (compose передаёт их в контейнер), пустые значения безвредны.
После правки `.env` нужен `docker compose -f docker-compose.prod.yml up -d --force-recreate backend`
(и то же для `postgres`, если меняли его переменные). Просто `up -d` может ответить
«Container … Running» и **не пересоздать** контейнер: compose не всегда считает изменение
значений в `.env` поводом для пересоздания, и тогда новые настройки молча не применяются —
проверено на `S3_*` и `NOTIFY_*`. Признак, что не применилось: `docker compose exec backend
printenv STORAGE_DRIVER` пуст, а в журнале нет строки про хранилище. Сам файл compose
приходит из репозитория и обновлением перезаписывается, а `.env` обновление не трогает,
поэтому все настройки стенда живут именно там.

Адрес сервера моделей задавать в `.env` не обязательно: каждый пользователь добавляет свои
серверы прямо в окне помощника («Настройка» → «Свои серверы моделей», до 5 на человека,
`GET/POST/DELETE /api/ai/endpoints`). Свой сервер становится обычным провайдером с
идентификатором `own:<uuid>`; ключ к нему (если сервер его требует) хранится шифртекстом в
той же записи и требует заданного `AI_SECRET_KEY`. Переменные `AI_OLLAMA_URL` /
`AI_OPENAI_COMPAT_URL` остаются для сервера, общего для всего стенда. Подробности и разбор
компромисса с локальными адресами — `docs/ai-assistant.md` §3.9.

## Тесты

```bash
# Backend unit + integration (нужна Postgres; интеграционные тесты feed
# создают себе отдельную базу <TEST_DATABASE_URL>_feed и применяют миграции сами)
cd backend && go test ./...

# Frontend unit
cd frontend && npm test

# Хранилище вложений: контракт ObjectStore прогоняется по ОБЕИМ реализациям — на диске
# (всегда) и против настоящего S3 (если задан S3_TEST_ENDPOINT; в CI это отдельный job).
# Готовый docker-запуск сервера и что именно проверяется — docs/storage-s3.md §12.
cd backend && S3_TEST_ENDPOINT=http://127.0.0.1:9010 S3_TEST_ACCESS_KEY=confkey \
  S3_TEST_SECRET_KEY=confsecret S3_TEST_BUCKET=skyfraze-conformance \
  go test ./internal/storage/ -run Conformance -v

# E2E в браузере (Playwright): регистрация на пустой инсталляции, вход,
# защищённые страницы, загрузка проекта, прокрутка, помощник. Vite Playwright
# поднимает сам, а backend должен быть запущен на :8181 (docker compose up или
# go run ./cmd/server) — на него смотрит прокси в frontend/vite.config.ts
cd frontend && npm run e2e

# Сценарии идут двумя проектами: `install` (регистрация первого администратора на
# пустой базе) объявлен первым и в CI НЕ имеет права пропускаться — остальные входят
# уже созданной им учётной записью. Поэтому проверка «на чистой инсталляции есть
# первый администратор» действительно выполняется, а не рапортует «skipped».
#
# Прогнать те же сценарии против уже поднятого стенда, не поднимая свой vite:
cd frontend && E2E_BASE_URL=http://localhost:5173 E2E_NO_SERVER=1 npx playwright test
```

**Режим регистрации для e2e — `request`, как в CI.** `install.spec.ts` проверяет именно первую
регистрацию владельца стенда: на пустой базе страница обязана показывать «Первый администратор».
При `REGISTRATION_MODE=open` там «Регистрация», и сценарий падает — не потому, что что-то
сломалось, а потому, что проверялось не то. В `.github/workflows/ci.yml` это записано явно
(`REGISTRATION_MODE: request`), и локальный прогон должен повторять CI. Обратная сторона: база
для e2e нужна **пустая** — если в ней уже есть люди, `install` честно скажет «инсталляция не
пустая» и уведёт за собой остальные сценарии.

**Что проверяет e2e и где взять базу для него.** Двадцать шесть сценариев: регистрация
первого администратора, вход, защищённые страницы, загрузка файлов, прокрутка, помощник
(создание главы и картинка), **правки агента по подтверждению** (предложение → применение
→ возврат и отклонение), **удаление кадра агентом и его отмена** (кадр исчезает из дерева и
возвращается на место), **поиск по тексту проекта**, **обсуждение кадра** (замечание
пишется, видно счётчиком в дереве, переживает перезагрузку и удаляется), **маркеры DOCX**
(панель «Разметка DOCX» вставляет разрыв и оглавление, текст доезжает до сервера — видно в
`export.md`, — а в показе служебных строк нет), **упоминания в кадре** (один чип на карточку,
счётчик вхождений, «ещё N», повторное нажатие ведёт к следующему месту) и **галочка писем о
замечаниях** (по умолчанию снята), **история версий** (сохранить, предпросмотр,
восстановление), **книга** (скачивание EPUB/DOCX с проверкой байтов), **корзина проектов**
(удалённый проект пропадает из списка, возвращается из корзины со сроком, скачивается
архивом и удаляется навсегда), **колокольчик** (видим в шапке, счётчика нет, панель честно
говорит «новых замечаний нет», Esc закрывает), **чат проекта** (сообщение переживает
перезагрузку, отметка ставится и снимается, «показать прежние» подгружает историю сверху),
**хронология карточки и перенос архивом** (кадр с упоминанием находится и открывается, а после
экспорта и импорта карточка по-прежнему связана с текстом), **правка фрагмента по замечанию**
(предложение помощника видно как диff «было → станет», применяется по кнопке и возвращается
«Вернуть прежний фрагмент»; а если человек успел поправить этот же абзац — отказ словами, а не
тихое применение) и **ключ доступа** (настоящая церемония
WebAuthn через виртуальный аутентификатор Chromium: привязка в профиле, коды восстановления,
вход ключом на втором шаге, удаление).
Локально нужна пустая база и backend на `:8181`:

```bash
docker exec skyfraze-postgres psql -U skyfraze -d postgres -c "create database skyfraze_e2e"
cd backend && go build -o /tmp/skyfraze-e2e ./cmd/server
DATABASE_URL=postgres://skyfraze:skyfraze_dev@localhost:5432/skyfraze_e2e?sslmode=disable \
JWT_SECRET=e2e-secret STORAGE_DIR=/tmp/skyfraze-e2e-storage LISTEN=:8181 \
CORS_ORIGINS=http://localhost:5173 AI_ENABLED=true AI_OLLAMA_URL=http://127.0.0.1:11490 \
AUTH_RATE_PER_MINUTE=0 AUTH_LOGIN_PER_EMAIL_PER_MINUTE=0 \
APP_BASE_URL=http://localhost:5173 REGISTRATION_MODE=request \
  /tmp/skyfraze-e2e &                       # + заглушка: node frontend/tests/e2e/stub-ollama.mjs
cd frontend && CI=1 npx playwright test    # CI=1 обязателен, см. ниже
```

**Почему `APP_BASE_URL` нужен и здесь.** Ключи доступа (WebAuthn) включаются только при
известном публичном адресе: RP ID и origin берутся из него, а не из заголовка запроса. В e2e
это адрес vite — тогда RP ID `localhost`, и виртуальный аутентификатор Chromium в сценарии
`zz-passkeys.spec.ts` проходит настоящую церемонию. Без переменной раздел ключей в профиле
скрыт, и сценарий упадёт на «backend не настроен» — это и есть его проверка.

**Почему ограничитель входа выключен.** Сценариев больше десяти, и каждый входит **тем же
адресом с того же IP**. `AUTH_LOGIN_PER_EMAIL_PER_MINUTE` (5 по умолчанию) начинает отвечать
`429` на законный вход, и падают не все сценарии, а «случайные» — с «неверный email или
пароль» в разметке, то есть прогон выглядит нестабильным, хотя нестабилен не он. Сам
ограничитель проверяется отдельно (`internal/ratelimit` и интеграционные тесты auth); в
браузерных сценариях он — не предмет проверки, а помеха. В том же виде это задано в CI.

**Ловушка локального запуска:** `docker compose` публикует фронтенд на `5173`, а Playwright
поднимает свой vite с `reuseExistingServer: !CI`. Без `CI=1` сценарии молча пойдут в
докер-фронтенд — то есть на рабочий стенд: тесты «пройдут», а данные запишутся в чужую базу
(и помощник будет отвечать не заглушкой). `CI=1` заставляет Playwright поднять свой сервер.

**Ещё одна, найденная на своих же прогонах:** полный набор рассчитан на ОДИН свежий backend и
ОДНУ пустую базу. Если база не пуста, `install.spec.ts` в CI честно падает («инсталляция не
пустая»), а следом падают все, кто входит этой учётной записью. Если рядом с e2e-backend
живёт второй сервер (например, от прошлого прогона, или docker-стенд на том же порту),
картина становится случайной: часть сценариев получает «Сервер не ответил вовремя», а в
разметке упавшего — «Неверный email или пароль» при верном пароле. Проверка перед прогоном:
`curl -s localhost:8181/api/auth/config` должен вернуть `"bootstrap":true`, а
`Get-Process skyfraze-e2e` — ровно один процесс.

**Живые проверки и диагностика.** Скрипты в `frontend/tests/` — инструменты на живом стенде, а не
тесты: они создают проекты, снимают скриншоты и печатают числа для человека, поэтому в CI не
гоняются (там только `go test ./...`, `npm test` и `npm run e2e`). Каталог всех скриптов — по
предложению на каждый, с указанием, что он меряет и что ему нужно, — `docs/diagnostics.md`.
Самые употребительные:

```bash
# снимки для ГЛАЗ: блок «Связи проекта» и профиль «Вход и устройства», 1280 и 390 px
cd frontend && npx tsx tests/visual-entities.ts
cd frontend && npx tsx tests/visual-profile.ts

# список связей в карточке и его поведение под нагрузкой (20 связей, 1280 и 360 px)
cd frontend && npx tsx tests/diag-entity-links.ts
cd frontend && npx tsx tests/diag-entity-links-load.ts

# переименование карточки не теряет связи с текстом; замер пересчёта упоминаний
cd frontend && npx tsx tests/diag-entity-rename.ts
cd frontend && npx tsx tests/diag-mentions-perf.ts
```

## Аудит панели (скилл `ui-visual-audit`)

Проектный скилл (`.dsh/skills/ui-visual-audit`) проверяет **восприятие** интерфейса и
**работу каждой заявленной возможности** на живом стенде: обрезанный текст, элементы
вне экрана, перекрытые/недоступные контролы, мелкие цели нажатия, незагруженные
картинки, низкий контраст, перехват кликов fixed-слоями, ошибки сети, а также матрицу
функций (проекты, иерархия, ассеты, темы, роли/приглашения, realtime CRDT).

```bash
cd frontend
npx tsx ../.dsh/skills/ui-visual-audit/scripts/visual-audit.ts              # визуал + функции
ONLY_SCREENS=1 npx tsx ../.dsh/skills/ui-visual-audit/scripts/visual-audit.ts    # только визуал
ONLY_FUNCTIONAL=1 npx tsx ../.dsh/skills/ui-visual-audit/scripts/visual-audit.ts # только функции
```

Отчёт: `_audit_out/visual-report.md` (+ `.json`) со скриншотами и указанием, какой файл
править; код выхода 1, если есть ошибки. Тестовые проекты скилл создаёт и удаляет сам.

**Где взять проект для аудита.** Визуальной части нужен существующий проект с содержимым
(стадия, дерево, «Связи», чат): без него экраны проекта пустые, и проверка «зелёная» ни о чём.
На dev-стенде это постоянный проект (`AUDIT_PROJECT=<id>`), а в CI его создаёт
`frontend/tests/audit/seed-project.ts`: учётка (в пустой базе первый человек — администратор),
проект, **импорт Markdown** с главой и двумя кадрами, две карточки со связью, сообщение в чате и
публикация. Печатает готовые `AUDIT_EMAIL`, `AUDIT_PASS`, `AUDIT_PROJECT_ID`:

```bash
cd frontend && npx tsx tests/audit/seed-project.ts | tee /tmp/seed.log
# дальше — подставить вывод скрипта в окружение аудита
```

**Почему импорт Markdown, а не `POST /events`.** Эта ручка пишет только таблицу событий, а стадия
и дерево читают документ CRDT: проект с «табличными» событиями открывается как «Таймлайн пока
пуст». Импорт идёт тем же путём, что и помощник (`LiveDoc` + `SetEventTextLive`), поэтому документ
и таблица согласованы. Скрипт проверяет это сам — дерево и документ после импорта обязаны быть
непустыми, иначе падает: иначе аудит молча шёл бы по пустым экранам (так и случилось в первом
ночном прогоне).

## Ночные проверки (`.github/workflows/nightly.yml`)

Аудит и охота за флейками идут **не в блокирующем `ci.yml`, а по расписанию** (03:17 UTC) и
вручную через `workflow_dispatch`. Так падение вёрстки не останавливает срочный фикс бэкенда, но
и не остаётся незамеченным: два прогона в статусе сборки, отчёт артефактом.

**Что гоняется:**

| Job | Что делает | Зачем |
|---|---|---|
| `unit-repeat` | `vitest run` три раза | у unit один прогон и нет повторов: один флейк — красный CI, но имя нестабильного теста из одного падения не видно |
| `audit` | свежий Postgres + backend + заглушка модели + vite, `seed-project.ts`, затем `visual-audit.ts` с `ONLY_SCREENS=1` | визуальные регрессии (обрезанный текст, элемент за краем, перекрытые контролы, контраст, мелкие цели) раньше ловились только руками на dev-стенде |
| `e2e-repeat` | два полных прогона e2e на **разных чистых базах** (backend перезапускается) | второй прогон ловит случайности в браузере; повтор на той же базе невозможен: `install` проверяет первую регистрацию, а ключ доступа выдаёт коды восстановления только при привязке первого ключа |

Полный аудит (экраны + функциональная матрица) — вручную:
`gh workflow run nightly.yml -f functional=true`.

**Почему свежая база и почему `REGISTRATION_MODE=open` в `audit`.** Скрипт подготовки данных
регистрирует первую учётку (в пустой базе она становится администратором — иначе экран `/admin`
открывать нечем), создаёт проект, главу, два кадра, две карточки со связью и сообщение в чате,
затем публикует проект, чтобы у аудита были и публичные экраны. На dev-стенде (регистрация
закрыта) скрипт не падает: он сначала пробует войти существующей учёткой `AUDIT_EMAIL`.

## Хранение на сервере

Что занимает место и что с этим делать по шагам — `docs/storage-compression.md`.
План по S3/MinIO (что даёт, что ломает, почему пока не делаем) — `docs/storage-s3.md`.
История версий проекта (снимки по ходу работы, «верни как было час назад») — `docs/versions.md`.
Резервные копии — `docs/backups.md`; коротко:

```bash
bash deploy/backup.sh                 # копия базы и вложений в backups/<дата>
bash deploy/backup.sh --drill         # проверить, что копия восстанавливается
sudo bash deploy/install-backup-units.sh   # ежедневный таймер (один раз, на хосте)
bash deploy/install-backup-units.sh --user # то же без root (если sudo просит пароль)
cp deploy/backup.env.example backup.env    # офсайт и хранение: BACKUP_RSYNC /
                                           # BACKUP_RCLONE / BACKUP_KEEP
```

**Без офсайта копии не спасают от потери машины:** `BACKUP_RSYNC` или `BACKUP_RCLONE`
нужно задать, иначе копии лежат на том же диске, что и данные (скрипт каждый раз пишет об
этом в журнал). Таймер без настроенного офсайта всё равно полезен — он закрывает
«удалил не тот проект» и порчу базы, но не отказ диска.

Отчёт о размерах доступен тремя способами:

- **страница `/admin` в интерфейсе** — раздел «Хранилище»: размеры базы, снапшотов
  (и самые тяжёлые проекты поимённо), текста проекции, вложений и каталога файлов,
  расхождения каталога с базой, кнопки «Убрать лишние файлы» и «Пережать картинки»
  (сначала сухой прогон, применение — отдельной кнопкой). Отчёт читается при
  открытии страницы: он только читает;
- SQL-скрипт на хосте со стендом:

```bash
# размеры таблиц, снапшоты (сырые и сжатые TOAST),
# дублирование текста, проекты-тяжеловесы, объём вложений
bash deploy/storage-report.sh
```

- API (то же, что делает экран; полезно в скриптах):

```bash
curl -H "Authorization: Bearer $TOKEN" http://<стенд>/api/admin/storage
curl -X POST -H "Authorization: Bearer $TOKEN" http://<стенд>/api/admin/storage/sweep
# пережатие уже загруженных картинок: без ?apply=1 — сухой прогон
curl -X POST -H "Authorization: Bearer $TOKEN" http://<стенд>/api/admin/storage/recompress
```

Файлы удаляются вместе с проектом, а раз в сутки сервер убирает то, что осталось от
удалённых проектов и прерванных импортов (карантин — сутки: свежий файл без строки в
базе может быть серединой чужого импорта).

Одинаковые файлы хранятся один раз: у вложения есть хеш содержимого (SHA-256), и
если такой файл уже загружен в любой проект, второй раз он не пишется — новая строка
вложений ссылается на существующий объект. Имя, владелец и проект у каждой строки
свои, а сам файл удаляется только с последней ссылкой на него.

Картинки пережимаются в WebP: PNG — без потерь (скриншоты и схемы с текстом портить
нельзя), JPEG — с потерями (качество 82) и с обрезкой длинной стороны до 2560 точек.
**HEIC с айфона тоже принимается**: сервер разбирает его утилитой `heif-convert`
(пакет `libheif-tools` в образе) и дальше ведёт как обычный JPEG — снимок
3200×2400 приезжает как **148 КБ вместо 5 МБ (×35)**. Если утилиты в образе нет,
сервер честно отказывает на HEIC («сохраните как JPEG»), а не хранит файл, который
браузер не покажет. С телефона снимок 3200×2400 q92 в JPEG приезжает как **161 КБ
вместо 2 МБ (×12.4)**. Если пережатие не выигрывает или файл не декодируется, он
остаётся как есть — пережатие улучшение, а не условие приёма. Уже загруженные
картинки пережимаются отдельным проходом:

```bash
# сухой прогон: покажет, сколько даст, и ничего не запишет
curl -X POST -H "Authorization: Bearer $TOKEN" http://<стенд>/api/admin/storage/recompress
# применить
curl -X POST -H "Authorization: Bearer $TOKEN" 'http://<стенд>/api/admin/storage/recompress?apply=1'
```

Оригиналы при этом не сохраняются: страница показывает картинку, а не готовит её к
печати. Подробности и замеры — `docs/storage-compression.md`.

**Квота на проект.** Предел суммы вложений — `ASSET_QUOTA_BYTES` (по умолчанию
**10 МиБ**, `0` — без предела). Считается по весу **после пережатия**: снимок с
телефона на 8 МБ приезжает как 300 КБ и занимает 300 КБ. В панели редактора видно
«Файлы проекта · 8.4 МБ из 10.0 МБ», а при отказе сервер объясняет его словами:
«занято 9.4 МБ из 10.0 МБ — файл на 1.2 МБ не помещается». Место освобождает
удаление файла (кнопка в том же списке); файл, прикреплённый к кадрам, удалить
нельзя — `409` и просьба сначала открепить: ссылка живёт в CRDT-документе.
