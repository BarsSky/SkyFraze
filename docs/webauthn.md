# Ключи доступа (WebAuthn): разбор перед кодом

Документ-разбор, а не реализация: что нужно, чтобы второй фактор был не только TOTP, и какие
решения придётся принять один раз и навсегда.

## 1. Что изменилось: домен и TLS есть

Раньше WebAuthn был заблокирован, и причина была записана честно: стенд отдавался по
`http://192.168.13.66`, а браузер даёт WebAuthn только в **secure context** (HTTPS или
localhost). Проверено сейчас:

| Что | Факт |
|---|---|
| DNS | `fraze.skynas.ru` → `95.165.170.190` |
| HTTPS | `https://fraze.skynas.ru/api/health` → `200`, `v0.63.0` |
| Сертификат | `CN=fraze.skynas.ru`, Let's Encrypt (`YE2`), действует до **26.12.2026** |
| Где TLS | **не на стенде**: на хосте нет слушателя на 443, сертификат и прокси — на периметре (фронт стенда слушает только `:80`) |
| API через домен | `/api/projects` без токена → `401`, `/api/public/feed` → `200` |
| Опечатка в `.env` стенда | `CORS_ORIGINS` содержал `fraza.skynas.ru`; исправлено на `fraze.skynas.ru`, добавлен `APP_BASE_URL=https://fraze.skynas.ru` |

Значит: origin для WebAuthn — `https://fraze.skynas.ru`. Больше **ничего** для запуска не нужно.

## 2. Решение, которое нельзя поменять потом: RP ID

WebAuthn привязывает ключ к **Relying Party ID** — домену. Ключ, созданный для
`fraze.skynas.ru`, не будет работать для `skynas.ru` и наоборот (в сторону поддомена — можно,
в сторону родителя — нет).

**Рекомендую `fraze.skynas.ru`** — самый узкий вариант:

- ключи этого приложения не станут ключами к другим сервисам `skynas.ru` (а там уже живут
  MinIO и что-то ещё появится);
- «принцип наименьших прав» здесь буквальный: RP ID — это область, где ключ действует;
- обратный переход (захотим потом общий ключ для всех сервисов) — это пересоздание ключей
  пользователями, то есть одномоментно неудобно, но возможно. Обратный путь хуже: если начать
  с `skynas.ru`, приложение уже не сможет отличить «мой ключ» от «ключа соседа».

Если решишь иначе — скажи до реализации: после неё это миграция ключей у людей.

## 3. Что именно добавляем

Второй фактор сейчас — TOTP (0.53.0). Ключи доступа добавляются как **вторая опция второго
фактора**, а не замена:

- **вход:** пароль → (если включён второй фактор) выбор «код из приложения» или «ключ/отпечаток»;
- **включение:** в профиле «Добавить ключ доступа» → браузер просит отпечаток/Face ID/PIN →
  сервер проверяет и сохраняет публичный ключ. Имя ключа даёт человек («ноутбук», «телефон»);
- **несколько ключей** на человека: потеря одного устройства — не потеря аккаунта;
- **коды восстановления остаются** общими для обоих способов: это последний путь в аккаунт, и
  он не должен зависеть от того, каким фактором человек пользовался.

**Чего сознательно не делаем в первой версии:**

- **вход без пароля** (passkey как первый фактор, discoverable credentials) — отдельный UX и
  отдельный риск: «ключ вместо пароля» ломает восстановление, а у нас нет сброса по почте;
- **проверку аттестации** (кто именно произвёл ключ: YubiKey, Apple, …) — attestation
  `none`-формата достаточно: нам нужен факт владения ключом, а не модель устройства;
- **условный UI** (`conditional`/autofill через `mediation: 'conditional'`) и **кросс-девайс**
  (гибридные транспорты) — их поддерживает не каждый браузер, а выигрыш только в удобстве;
- **сброса ключей администратором** — по той же причине, что и сброса TOTP: сброс второго
  фактора означает «можно войти без него».

## 4. Библиотека, а не свой код

Все прошлые «свои» вещи в проекте (SigV4, TOTP, EPUB) были оправданы: там 80–200 строк и
формат, который можно проверить тестовым вектором. WebAuthn — другое: CBOR, COSE-ключи,
разбор `authenticatorData`, проверка подписи по алгоритмам, флаги (UV/UP/BE/BS), challenge и
origin/rpId-проверки. Ошибка здесь — не «не работает», а «работает, но проверяет не то».

Поэтому берём **`github.com/go-webauthn/webauthn`** — канонический Go-пакет (им пользуются и
крупные проекты). Это зависимость, и её надо назвать вслух: в проекте их мало намеренно.

## 5. Данные

```sql
-- 0028_webauthn
CREATE TABLE user_webauthn_credentials (
    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    credential_id bytea NOT NULL UNIQUE,       -- id ключа от аутентификатора
    public_key    bytea NOT NULL,             -- COSE-ключ
    sign_count    bigint NOT NULL DEFAULT 0,   -- защита от клонирования (если даёт аутентификатор)
    transports    text NOT NULL DEFAULT '',   -- usb | nfc | ble | internal | hybrid
    aaguid        text NOT NULL DEFAULT '',
    name          text NOT NULL DEFAULT '',   -- «ноутбук», «телефон» — даёт человек
    created_at    timestamptz NOT NULL DEFAULT now(),
    last_used_at  timestamptz
);

-- challenge живёт минуты и только на сервере: в браузере его хранить нельзя (это и есть защита
-- от подмены). Отдельная таблица, а не память процесса: сервер перезапускается, а человек в
-- этот момент нажимает «подтвердить».
CREATE TABLE webauthn_challenges (
    id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    uuid REFERENCES users(id) ON DELETE CASCADE,
    kind       text NOT NULL,      -- register | login
    challenge  bytea NOT NULL,
    session    jsonb NOT NULL,     -- состояние церемонии (go-webauthn)
    created_at timestamptz NOT NULL DEFAULT now(),
    expires_at timestamptz NOT NULL
);
```

`sign_count` хранится и сверяется, но **не блокирует** вход при расхождении: часть платформенных
аутентификаторов всегда отдаёт ноль. Расхождение пишется в журнал как подозрительное — это
наблюдение, а не приговор человеку.

## 6. API и поток

Реализовано так (0.64.0):

```
# личный профиль (нужен вход)
GET    /api/auth/keys                        → список ключей (имя, дата, последний вход)
POST   /api/auth/keys/register/begin         → publicKey-опции + challenge_id
POST   /api/auth/keys/register/finish?challenge=<id>&name=<имя>
                                             → ключ сохранён (+ коды восстановления, если их не было)
DELETE /api/auth/keys/{id}                   → удалить ключ

# второй шаг входа (публичные, но требуют пропуск, выданный после пароля)
POST   /api/auth/login/webauthn/begin  {challenge}   → publicKey-опции + challenge_id
POST   /api/auth/login/webauthn/finish?challenge=<id> → токены
```

Два отличия от первоначального наброска — оба про то, где лежат данные:

- **имя ключа и `challenge_id` едут в строке запроса, а не в теле.** Тело ответа
  аутентификатора (`attestationObject`, `authenticatorData`, `signature`) разбирает сама
  библиотека из `*http.Request`. Если положить рядом свои поля, тело придётся разбирать и
  собирать заново — и ошибка в этом месте означала бы «подпись проверена не над тем, что
  пришло»;
- **вход ключом начинается с пропуска второго шага, а не с email.** Ключ — второй фактор:
  сначала пароль (`POST /api/auth/login` → `{totp_required, challenge, totp, passkeys}`), потом
  либо код из приложения (`POST /api/auth/login/2fa`), либо ключ. Знание «у кого есть ключи»
  тем самым никому не выдаётся, и потерянный ключ не запирает человека снаружи — пароль у него
  остаётся.

Правила, которые зашиты в код:

- **register только после полноценного входа** (пароль + второй фактор): иначе чужой с
  украденным паролем привяжет свой ключ;
- **challenge одноразовый** и удаляется при любом исходе (`DELETE … RETURNING`);
- **origin и rpId проверяет библиотека**, а мы передаём `https://fraze.skynas.ru` из
  `APP_BASE_URL` (не из заголовка запроса: заголовок приходит от прокси и ему нельзя верить);
- **удаление последнего ключа не выключает второй фактор**: TOTP остаётся, коды восстановления
  тоже;
- **ключ = второй фактор, а не «декорация»**: если ключи привязаны, одного пароля недостаточно
  (`Login` требует второй шаг и при выключенном TOTP);
- **коды восстановления выдаются при привязке первого ключа**, если их ещё нет. Иначе человек,
  включивший только ключ, при потере телефона остался бы без последнего пути в аккаунт.
  Коды показываются один раз; `LoginTOTP` принимает код восстановления и тогда, когда TOTP
  не включён вовсе;
- **`aaguid` хранится hex-строкой.** Сырой AAGUID содержит нулевые байты, и PostgreSQL
  отвергает такую строку в текстовой колонке (`invalid byte sequence for encoding UTF8`) —
  это выяснилось на первом же прогоне интеграционного теста.

## 7. Интерфейс

Сделано в 0.65.0:

- профиль → «Вход и устройства» → блок **«Ключи доступа»**: список привязанных ключей (имя,
  когда привязан, когда им последний раз входили, как подключён), «Привязать ключ», «Удалить» с
  подтверждением. Если ключей нет — объяснение, зачем их два («телефон и ноутбук»). Если ключей
  ещё нет и браузер не умеет WebAuthn — об этом сказано словами, а не пустым блоком;
- при привязке первого ключа показываются **коды восстановления** (8 штук, один раз): в базе
  только хеши, и это единственный момент, когда они существуют в открытом виде;
- вход: после пароля, если у человека есть и TOTP, и ключи — **две кнопки**: «Код из приложения»
  и «Войти ключом доступа». Если только ключи — сразу предложение ключа, поля кода нет вовсе
  (кода у такого человека не существует). Если только код — кнопки ключа нет;
- ошибки словами: «ключ не подтверждён — окно закрылось или время вышло», «такой ключ уже
  привязан», «этот браузер не поддерживает ключи доступа».

Почему блок в профиле, а не галочка: у ключа есть устройство, имя и срок. Список отвечает на
вопрос «что у меня привязано», и без него человек не узнал бы, что старый телефон всё ещё
открывает аккаунт.

### Что проверяет Go-интеграция (0.64.0)

`backend/internal/auth/webauthn_integration_test.go` собирает те же байты, что присылает браузер
(clientDataJSON, authData, COSE-ключ, подпись ES256), а не «вызовы с флагом
`verified=true`». Семь тестов:

| Тест | Что доказывает |
|---|---|
| `TestWebAuthnRegisterAndLogin` | привязка сохраняет ключ, вход им выдаёт токены, счётчик подписей и время входа записаны |
| `TestWebAuthnChallengeIsOneShot` | повтор того же ответа отвергается (одноразовость) |
| `TestWebAuthnRejectsForeignOrigin` | ответ с чужого origin не проходит, и ключ не сохраняется |
| `TestWebAuthnRejectsBadSignature` | испорченная подпись не даёт войти |
| `TestWebAuthnLoginStartRequiresTicket` | без пропуска второго шага вход ключом не начинается |
| `TestWebAuthnRecoveryCodeWithoutTOTP` | код восстановления работает, когда второй фактор — только ключ, и гасится после первого использования |
| `TestWebAuthnDisabledWithoutBaseURL` | без `APP_BASE_URL` ручки говорят «не настроено», а не падают |

Все четыре фазы закрыты. Что осталось за рамками первой версии — записано в §3 (вход без
пароля, проверка аттестации, условный UI, кросс-девайс, сброс администратором) и в §9.

### Что проверяет e2e (0.65.0)

`frontend/tests/e2e/zz-passkeys.spec.ts` — **настоящая церемония WebAuthn в Chromium**: окно
аутентификатора заменяет CDP (`WebAuthn.enable` + `addVirtualAuthenticator`), а всё остальное
как у человека — `navigator.credentials.create()` и `get()`, base64url, подпись ES256.

Сценарий: вход → профиль → привязка ключа («виртуальный ключ») → **8 кодов восстановления
показаны один раз** → выход → вход паролем → второй шаг предлагает ключ → вход ключом доводит
до `/projects` → удаление ключа → вход снова по одному паролю.

Две вещи, которые пришлось решить именно из-за e2e:

- файл назван `zz-`: сценарий заводит учётной записи второй фактор, и после него вход одним
  паролем перестаёт работать. Playwright запускает файлы по алфавиту, поэтому сценарий обязан
  идти **последним** — иначе остальные упирались бы во второй шаг. Ключ в конце удаляется,
  чтобы повторный прогон на той же базе начинался с того же состояния;
- backend в e2e получил `APP_BASE_URL=http://localhost:5173` (в CI и в README): RP ID `localhost`
  и origin vite — единственная комбинация, в которой Chromium считает контекст защищённым и
  пускает WebAuthn без HTTPS.

## 9. Решения, принятые до кода

1. **RP ID = `fraze.skynas.ru`** (рекомендация выше; решение необратимо без пересоздания ключей).
2. **Ключ — второй фактор, а не замена пароля** (первая версия).
3. **Коды восстановления общие** для TOTP и ключей.
4. **`sign_count` не блокирует вход**, только журнал.
5. **Библиотека `go-webauthn/webauthn`** — осознанная зависимость.

Все пять в силе после реализации. Одна поправка по итогам: ключ, привязанный человеком,
**включает второй шаг и при выключенном TOTP** — иначе «второй фактор» был бы украшением, а
пароль оставался бы единственным, что проверяется. Отсюда же обязанность выдавать коды
восстановления при привязке первого ключа.
