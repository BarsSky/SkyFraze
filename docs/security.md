# Безопасность входа

Короткий документ о том, что сделано против перебора паролей, и о том, чего сознательно нет.
Написан по факту: сначала был пробел (можно было перебирать пароль без ограничений), потом
появилась защита (0.51.0).

## 1. Что защищено сейчас

**Ограничение попыток входа** (`backend/internal/ratelimit`) — две независимые границы на
минуту:

| Граница | Что останавливает | Настройка |
| --- | --- | --- |
| по адресу клиента | веер попыток по разным аккаунтам с одной машины | `AUTH_RATE_PER_MINUTE` (по умолчанию 30, `0` — выключить) |
| по аккаунту (email) | перебор ОДНОГО пароля с разных адресов (ботнет, прокси) | `AUTH_LOGIN_PER_EMAIL_PER_MINUTE` (по умолчанию 5, `0` — выключить) |

Почему именно две. Только по адресу нельзя: за обратным прокси все клиенты приходят с одного
адреса, и общий счётчик заблокировал бы вход всем. Только по аккаунту мало: он не мешает
перебирать много разных аккаунтов с одной машины.

Граница по аккаунту проверяется **до** сверки пароля (bcrypt): дорогую часть не должен
оплачивать тот, кто уже превысил предел. Поэтому при активном переборе **верный пароль тоже
получает 429** — это не ошибка, а смысл защиты: аккаунт на минуту закрыт для всех, и
взломщик узнаёт об этом так же, как владелец.

Ответ — `429` с `Retry-After` в секундах и текстом «слишком много попыток входа — подождите и
попробуйте снова».

**Адрес клиента за прокси.** `X-Forwarded-For` принимается только когда непосредственный
сосед — локальный или приватный адрес (у стенда порт опубликован у nginx, до backend снаружи
не достучаться). Из цепочки берётся **последний** элемент: nginx дописывает настоящий адрес в
конец, и подделать его клиент не может.

**Уборка.** Окна живут в памяти процесса и выбрасываются раз в 10 минут. Ограничение —
память процесса: при нескольких инстансах backend счётчики не разделяются (для стенда это
верно — один backend; при масштабировании сюда придёт общий Redis).

## 2. Что проверено

- `backend/internal/ratelimit/ratelimit_test.go` — арифметика окна, независимость ключей,
  нормализация email (регистр и пробелы не обходят ограничение), `0` выключает границу,
  разбор адреса за прокси (включая цепочку и попытку подделки заголовка), уборка не трогает
  активные окна.
- **Живая проверка на настоящем сервере** (2026-10-25, `AUTH_LOGIN_PER_EMAIL_PER_MINUTE=3`):
  три неверных попытки → `401`, четвёртая и пятая → `429`, и **вход с верным паролем в это же
  окно тоже `429`**; другой аккаунт при этом входит нормально (`200`). После минуты вход
  восстанавливается.

## 3. Чего нет (и это осознанно)

- **Второго фактора (2FA/TOTP)** — пароль остаётся единственным. Для публичного сервиса это
  следующий шаг; для нынешнего использования (закрытая инсталляция, круг авторов) —
  приемлемо, но записано, чтобы не выглядело забытым.
- **Подтверждения email** при регистрации: адрес не проверяется, письмо может не дойти, и
  аккаунт всё равно работает. Сейчас регистрация и так по заявке или по приглашению.
- **Отзыва сессий и списка активных устройств**: refresh-токены хранятся в базе, выход
  завершает свою сессию, но «выкинуть все остальные» одной кнопки нет.
- **Аудита входов** (кто и откуда входил): в журнале есть только предупреждение о превышении
  попыток, истории «входов с новых адресов» нет.

## 4. Что ещё закрывает публичный контур

- **Регистрация по заявке** (по умолчанию) — аккаунт не появится без одобрения администратора.
- **Права по ролям** на всех данных: владелец/редактор/читатель; чтение проверяется на каждом
  запросе, а не в интерфейсе.
- **Согласия на утечку текста наружу**: отправка текста модели и письма о замечаниях
  включаются только человеком (по умолчанию выключены) — см. `docs/ai-assistant.md` и
  `docs/comments.md` §5.2.
