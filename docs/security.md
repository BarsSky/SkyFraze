# Безопасность входа

Короткий документ о том, что сделано против перебора паролей, и о том, чего сознательно нет.
Написан по факту: сначала был пробел (можно было перебирать пароль без ограничений), потом
появилась защита (0.51.0).

## 1. Что защищено сейчас

**Ограничение попыток входа** (`backend/internal/ratelimit`) — две независимые границы на
минуту:

| Граница | Что останавливает | Настройка |
| --- | --- | --- |
| по адресу клиента | веер попыток по разным аккаунтам с одной машины | `AUTH_RATE_PER_MINUTE` (по умолчанию 30, `0` — выключить) |
| по аккаунту (email) | перебор ОДНОГО пароля с разных адресов (ботнет, прокси) | `AUTH_LOGIN_PER_EMAIL_PER_MINUTE` (по умолчанию 5, `0` — выключить) |

Почему именно две. Только по адресу нельзя: за обратным прокси все клиенты приходят с одного
адреса, и общий счётчик заблокировал бы вход всем. Только по аккаунту мало: он не мешает
перебирать много разных аккаунтов с одной машины.

Граница по аккаунту проверяется **до** сверки пароля (bcrypt): дорогую часть не должен
оплачивать тот, кто уже превысил предел. Поэтому при активном переборе **верный пароль тоже
получает 429** — это не ошибка, а смысл защиты: аккаунт на минуту закрыт для всех, и
взломщик узнаёт об этом так же, как владелец.

Ответ — `429` с `Retry-After` в секундах и текстом «слишком много попыток входа — подождите и
попробуйте снова».

**Адрес клиента за прокси.** `X-Forwarded-For` принимается только когда непосредственный
сосед — локальный или приватный адрес (у стенда порт опубликован у nginx, до backend снаружи
не достучаться). Из цепочки берётся **последний** элемент: nginx дописывает настоящий адрес в
конец, и подделать его клиент не может.

**Уборка.** Окна живут в памяти процесса и выбрасываются раз в 10 минут. Ограничение —
память процесса: при нескольких инстансах backend счётчики не разделяются (для стенда это
верно — один backend; при масштабировании сюда придёт общий Redis).

## 2. Что проверено

- `backend/internal/ratelimit/ratelimit_test.go` — арифметика окна, независимость ключей,
  нормализация email (регистр и пробелы не обходят ограничение), `0` выключает границу,
  разбор адреса за прокси (включая цепочку и попытку подделки заголовка), уборка не трогает
  активные окна.
- **Живая проверка на настоящем сервере** (2026-10-25, `AUTH_LOGIN_PER_EMAIL_PER_MINUTE=3`):
  три неверных попытки → `401`, четвёртая и пятая → `429`, и **вход с верным паролем в это же
  окно тоже `429`**; другой аккаунт при этом входит нормально (`200`). После минуты вход
  восстанавливается.

## 3. Второй фактор входа (TOTP, 0.53.0)

Пароль можно украсть, подсмотреть или подобрать — лимит попыток (§1) этого не отменяет.
Поэтому появился **второй фактор по TOTP** (RFC 6238): код считает телефон человека, сервер
только проверяет его. Никаких SMS, писем и внешних сервисов — поэтому это работает на стенде
без дополнительных настроек.

Как устроено:

- **Включение — с подтверждением.** Профиль → «Включить двухфакторный вход»: сервер выдаёт
  секрет (base32) и ссылку `otpauth://`, человек вводит код из приложения, и только после
  этого вход становится двухфакторным. Пока код не подтверждён, вход — по одному паролю:
  опечатка при настройке не должна запирать снаружи.
- **Коды восстановления** — 8 штук, показываются **один раз** (в базе только SHA-256).
  Каждый одноразовый: потраченный код больше не принимается. Это замена телефона, а не
  «второй пароль на всякий случай» — сброса пароля по почте в проекте нет.
- **Вход — два шага.** Пароль → сервер отвечает `{"totp_required": true, "challenge": "…"}`
  → код → токены. Пропуск между шагами живёт **5 минут** и годится только для второго шага:
  refresh-токен или access в его роли отвергаются (тип токена проверяется).
- **Перебор кода ограничен** теми же границами, что и вход (§1): попытки по пропуску и по
  человеку считаются отдельно.
- **Выключение требует кода** — иначе украденная сессия снимала бы защиту одной кнопкой.
  **Сброса 2FA администратором нет** намеренно: сброс означал бы «можно войти без второго
  фактора», и вся защита сводилась бы к тому, кто первый попросит.

Правильность TOTP проверена **официальными тестовыми векторами RFC 6238**
(`internal/auth/totp_test.go`: шесть известных моментов времени и кодов), окно ±1 шаг —
тестом, а весь путь включения/входа/кодов восстановления — интеграционными тестами
(`totp_integration_test.go`, 6 сценариев).

## 3.1. Активные сеансы

В профиле видно, **где человек вошёл**: браузер и система из `user-agent`, адрес и время.
Кнопка «Выйти на всех устройствах, кроме этого» отзывает остальные refresh-сессии: текущая
остаётся, отозванные больше не обмениваются на токены (проверено тестом).

Это ответ на «я вошёл на чужом компьютере и забыл выйти» — до 0.53.0 такого экрана не было
вовсе, хотя данные для него лежали в таблице `sessions` с самого начала.

## 4. Чего нет (и это осознанно)

- **Подтверждения email** при регистрации: адрес не проверяется, письмо может не дойти, и
  аккаунт всё равно работает. Сейчас регистрация и так по заявке или по приглашению.
- **Аудита входов** (кто и откуда входил): в журнале есть предупреждение о превышении
  попыток и отметка «письмо о замечаниях», истории «входов с новых адресов» нет.

## 3.2. Ключи доступа (WebAuthn)

Второй фактор, кроме кода из приложения: отпечаток, Face ID или PIN устройства. Разбор решений —
`docs/webauthn.md`, серверная часть — 0.64.0 (миграция `0028`).

- **Ключ — второй фактор, а не замена пароля.** Вход: пароль → второй шаг → «код из приложения»
  **или** «ключ доступа». Вход без пароля (discoverable credentials) сознательно не сделан:
  сброса пароля по почте у нас нет, и потерянный ключ запирал бы человека снаружи навсегда.
- **Если ключи привязаны, одного пароля уже недостаточно** — даже при выключенном TOTP. Иначе
  «второй фактор» был бы украшением.
- **Коды восстановления общие** для обоих способов и выдаются при привязке первого ключа, если
  их ещё нет: это последний путь в аккаунт при потере устройства. Показываются один раз.
- **Приватного ключа у сервера нет** — только публичный. Утечка базы не даёт войти под
  человеком (в отличие от пароля и секрета TOTP).
- **Проверки делает библиотека** `go-webauthn/webauthn`: подпись ES256, `rpIdHash`, origin,
  флаги UP/UV, CBOR/COSE. RP ID берётся из `APP_BASE_URL`, а не из заголовка запроса: заголовок
  приходит от прокси, и доверять ему в проверке origin нельзя.
- **`sign_count` не блокирует вход**: часть платформ всегда отдаёт ноль, поэтому расхождение —
  запись в журнал, а не отказ человеку.
- **Сброса ключей администратором нет** — по той же причине, что и сброса TOTP.

Проверено: 7 интеграционных тестов собирают те же байты, что присылает браузер (clientDataJSON,
authData, COSE-ключ, подпись ES256) — привязка и вход, одноразовость challenge, отказ на чужом
origin, отказ на испорченной подписи, вход только по пропуску второго шага, код
восстановления без TOTP, «не настроено» без `APP_BASE_URL`. Чего нет: e2e через браузерный
virtual authenticator (фаза 4 плана) и интерфейса профиля (фаза 3) — не спрятано, а записано
в `docs/webauthn.md` §8.

## 4. Чего нет (и это осознанно)

- **Подтверждения email** при регистрации: адрес не проверяется, письмо может не дойти, и
  аккаунт всё равно работает. Сейчас регистрация и так по заявке или по приглашению.

## 5. Что ещё закрывает публичный контур

- **Регистрация по заявке** (по умолчанию) — аккаунт не появится без одобрения администратора.
- **Права по ролям** на всех данных: владелец/редактор/читатель; чтение проверяется на каждом
  запросе, а не в интерфейсе.
- **Согласия на утечку текста наружу**: отправка текста модели и письма о замечаниях
  включаются только человеком (по умолчанию выключены) — см. `docs/ai-assistant.md` и
  `docs/comments.md` §5.2.
