# Резервные копии: что копируется, куда и как восстанавливать

Коротко: **база и файлы живут в одном экземпляре**, и без копий любая потеря машины,
диска или «удалил не тот проект» необратима. Скрипт `deploy/backup.sh` снимает копию
одной командой, проверяет её восстановление и умеет отправить на другую машину.

Почему это, а не S3/MinIO: объектное хранилище место не экономит и копией не является —
MinIO на том же диске умирает вместе с ним (разбор в `docs/storage-s3.md`). Копия на
другой машине закрывает тот же риск и не требует ни одной строки кода.

## 1. Что попадает в копию

Один каталог `backups/<год-месяц-день>_<время>/`:

| Файл | Что внутри | Чем восстанавливать |
| --- | --- | --- |
| `db.dump` | вся база: `pg_dump -Fc` | `pg_restore` |
| `db.toc` | оглавление дампа (таблицы, объекты) | читается глазами, `pg_restore -l` |
| `assets.tar.gz` | каталог вложений целиком (`STORAGE_DIR`) | `tar xzf` |
| `manifest.txt` | когда, где, версия, размеры, счётчики (проекты, люди, системные аккаунты, события, вложения, файлы) | — |
| `SHA256SUMS` | контрольные суммы `db.dump` и `assets.tar.gz` | `sha256sum -c` |

**Порядок важен: сначала база, потом файлы.** Если снимать наоборот, между двумя шагами
появится файл, строка о котором попадёт в дамп, — и в копии окажется вложение без файла
(кадр с пустым местом). Обратный случай безвреден: лишний файл без строки уборщик удалит
сам. Скрипт делает именно так, и `--drill` проверяет это соотношение.

## 2. Как снять копию

```bash
cd /home/skyadmin/skyfraze          # каталог стенда (там .env и docker-compose.prod.yml)
bash deploy/backup.sh                # копия в backups/<дата>
```

Что можно настроить (переменные окружения):

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `BACKUP_DIR` | `<каталог стенда>/backups` | куда складывать копии |
| `BACKUP_KEEP` | `7` | сколько копий хранить на месте (`0` — не удалять ничего) |
| `BACKUP_RSYNC` | пусто | `user@host:/path` — копия уезжает по ssh (`rsync` на обоих концах) |
| `BACKUP_RCLONE` | пусто | `remote:path` — копия уезжает через `rclone` (облако, S3, другой сервер) |
| `BACKUP_RCLONE_KEEP` | `0` | сколько копий хранить в офсайте (`0` — не удалять ничего; локальный `BACKUP_KEEP` к бакету не относится, `rclone copy` только добавляет) |
| `BACKUP_ASSETS_RCLONE` | пусто | `remote:path` — откуда брать вложения, если они лежат в S3 (`STORAGE_DRIVER=s3`, `docs/storage-s3.md` §10). Пусто — читаются с диска. Без этой строки при S3-хранилище копия осталась бы без файлов |

**Куда их писать.** В отдельный файл стенда `backup.env` рядом с `.env`:

```bash
cp deploy/backup.env.example /home/skyadmin/skyfraze/backup.env
# BACKUP_RSYNC=skyadmin@backup-host:/srv/backups/skyfraze
```

Его читает сам `deploy/backup.sh`, поэтому настройки одни и для ручного запуска, и для
таймера. **Не `.env`**: `.env` читает только `docker compose`, и строка `BACKUP_RSYNC`,
дописанная туда, не делала бы ничего — копии молча оставались бы на той же машине.
Переменная, заданная в шелле, главнее файла: `BACKUP_KEEP=3 bash deploy/backup.sh`.

**Офсайт — это и есть смысл копий.** Пока они лежат на той же машине, от потери машины
они не спасают: `BACKUP_RSYNC`/`BACKUP_RCLONE` нужно задать. Скрипт каждый раз пишет в
журнал, настроен офсайт или нет (`journalctl -u skyfraze-backup.service`).

### 2.1. Офсайт в S3 (MinIO) — как это сделано на боевом стенде

На стенде офсайт уезжает в **отдельный бакет** MinIO на NAS: тот же сервер, что хранит
бэкапы skygate, но свой бакет — чужие данные в нём не лежат, и квота/ротация у каждого
стенда свои.

```bash
# 1. rclone ставится БЕЗ root (sudo на стенде может просить пароль) — в ~/.local/bin.
#    deploy/backup.sh ищет его и в PATH, и там: PATH пользовательского юнита systemd
#    каталог ~/.local/bin не содержит, и без этого таймер писал бы «rclone не установлен»,
#    пока ручной запуск работает.
mkdir -p ~/.local/bin && cd /tmp \
  && curl -sSL -o rclone.zip https://downloads.rclone.org/rclone-current-linux-amd64.zip \
  && python3 -c "import zipfile,os,shutil;z=zipfile.ZipFile('rclone.zip');n=next(x for x in z.namelist() if x.endswith('/rclone'));z.extract(n,'/tmp/rx');shutil.copy2('/tmp/rx/'+n,os.path.expanduser('~/.local/bin/rclone'));os.chmod(os.path.expanduser('~/.local/bin/rclone'),0o755)" \
  && ~/.local/bin/rclone version | head -1

# 2. Remote в ~/.config/rclone/rclone.conf (права 600, ключи — от оператора MinIO):
cat > ~/.config/rclone/rclone.conf <<'CONF'
[skyfraze]
type = s3
provider = Minio
access_key_id = <ключ>
secret_access_key = <секрет>
endpoint = https://minio.<домен>
region = us-east-1
CONF
chmod 600 ~/.config/rclone/rclone.conf
~/.local/bin/rclone lsd skyfraze:            # бакет skyfraze должен быть виден

# 3. Офсайт в backup.env стенда (не в .env — его читает только docker compose):
echo 'BACKUP_RCLONE=skyfraze:skyfraze' >> ~/skyfraze/backup.env
# и, если бакет не должен расти вечно, — сколько копий там хранить:
echo 'BACKUP_RCLONE_KEEP=14' >> ~/skyfraze/backup.env

# 4. Проверка: копия уходит, скачивается и РАЗВОРАЧИВАЕТСЯ
bash deploy/backup.sh                       # в журнале: «офсайт: rclone → skyfraze:skyfraze»
~/.local/bin/rclone size skyfraze:skyfraze  # объекты появились
rm -rf /tmp/offsite && mkdir -p /tmp/offsite
~/.local/bin/rclone copy skyfraze:skyfraze/<дата-время> /tmp/offsite
(cd /tmp/offsite && sha256sum -c SHA256SUMS)
bash deploy/backup.sh --drill /tmp/offsite   # копия ПРИЕХАЛА и восстанавливается
```

**Чем это проверено (2026-10-25, стенд v0.46.0):** копия `2026-10-25_050631` (5.7 MB:
`db.dump` 315 KB, `assets.tar.gz` 5.4 MB) уехала в бакет, скачалась обратно, контрольные
суммы `SHA256SUMS` сошлись (`db.dump: OK`, `assets.tar.gz: OK`), а `--drill` развернул её
в отдельную базу: 3 проекта, 2 пользователя, 5 вложений, «файлов нет у вложений: 0».
Без шага 4 офсайт — это надежда: копия может уехать битой или не уехать вовсе.

**Стенд ходит в MinIO не ключами оператора (0.46.3).** Сначала бакет обслуживался
ключом оператора — то есть компрометация SkyFraze открывала и бакеты skygate. Теперь
заведён отдельный пользователь MinIO `skyfraze` с одной политикой:

```bash
# политика: только бакет skyfraze, ни списка бакетов, ни чужих префиксов
cat > skyfraze-rw.json <<'JSON'
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": ["arn:aws:s3:::skyfraze"] },
    { "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject",
                 "s3:AbortMultipartUpload", "s3:ListMultipartUploadParts"],
      "Resource": ["arn:aws:s3:::skyfraze/*"] }
  ]
}
JSON

# mc берётся из релизов на GitHub: dl.min.io отдаёт 410 (клиент архивирован)
curl -sSL -o ~/.local/bin/mc \
  https://github.com/minio/mc/releases/download/RELEASE.2025-08-13T08-35-41Z/mc.linux-amd64.RELEASE.2025-08-13T08-35-41Z
chmod 755 ~/.local/bin/mc

MC_HOST_op="https://<оператор>:<секрет>@minio.<домен>"   # только на время настройки
mc admin policy create op skyfraze-rw skyfraze-rw.json
mc admin user add op skyfraze "$(head -c 64 /dev/urandom | tr -dc 'A-Za-z0-9' | head -c 40)"
mc admin policy attach op skyfraze-rw --user skyfraze
# ключи пользователя — в ~/.config/rclone/rclone.conf (600), ключ оператора со стенда убрать
```

**Чем проверено:** `mc ls` от нового пользователя видит `skyfraze/`, а `skygate-backups`
отвечает `Access Denied`; полный список бакетов он тоже не видит (`mc ls` показывает только
свой). Обычный запуск копии через таймер после смены ключей — `Result=success`, копия
уехала, ротация отработала («копий в бакете: 3 (хранится 14)»).

## 3. Расписание

Ставятся **два** таймера: ежедневная копия и недельная проверка восстановления. Копия,
которую ни разу не восстанавливали, копией не считается — файлы могут быть битыми, а дамп
нечитаемым, и узнать об этом лучше в воскресенье, чем в день аварии.

```bash
# Системные юниты (нужен root — обычный путь на своём сервере):
sudo bash deploy/install-backup-units.sh
systemctl list-timers 'skyfraze-*'             # когда следующий запуск (копия и проверка)
sudo systemctl start skyfraze-backup.service   # копия прямо сейчас
sudo systemctl start skyfraze-drill.service    # проверка восстановления сейчас
journalctl -u skyfraze-backup.service -n 50    # что было в последнем запуске
journalctl -u skyfraze-drill.service -n 50     # и что сказала проверка

# Пользовательские юниты (root не нужен) — когда sudo просит пароль или его нет:
bash deploy/install-backup-units.sh --user
systemctl --user list-timers 'skyfraze-*'
systemctl --user start skyfraze-backup.service
systemctl --user start skyfraze-drill.service
journalctl --user -u skyfraze-drill.service -n 50
systemctl --user --failed                      # провал проверки видно здесь
```

Проверка идёт раз в неделю (воскресенье, 04:30 + разброс) — заведомо позже ночной копии:
проверять вчерашнюю, пока сегодняшняя пишется, значит проверять не то, что будет лежать в
бэкапе. Разворачивает копию в ОТДЕЛЬНУЮ базу и временный каталог, рабочую не трогает, за
собой убирает. Провал — это failed у юнита, а не тишина в журнале.

Системный режим — предпочтительный: юнит живёт независимо от входов в систему, его видно
в общем списке таймеров машины, и им управляет root. Режим `--user` существует потому, что
«нет sudo» не должно означать «нет копий»: скрипт ставит те же два юнита в
`~/.config/systemd/user`, сам включает `loginctl enable-linger` (иначе таймер умирает с
выходом из системы — на сервере, куда заходят по ssh, копий почти не было бы) и добавляет
в юнит ожидание Docker (`Persistent=true` запускает пропущенную копию сразу после загрузки,
когда dockerd может быть ещё не готов). Ограничения режима `--user`: юнита не видно в
системном `systemctl list-timers`, и `--drill` по расписанию не запускается — проверку
восстановления всё равно делают руками.

Юнит идёт от владельца каталога (не от root): `docker compose` читает `.env`, а копии
пишутся рядом с проектом, и root'овые каталоги потом не удалить при ротации. Владелец
должен быть в группе `docker` — иначе он не запускал бы `docker compose` вручную. Таймер —
`03:30` плюс случайный разброс до 10 минут, `Persistent=true`: если машина была
выключена, копия снимется при первом включении, а не пропустится до следующих суток.

## 4. Проверка: копия, которую не восстанавливали, копией не считается

```bash
bash deploy/backup.sh --drill                 # проверить последнюю копию
bash deploy/backup.sh --drill backups/2026-10-02_033012   # конкретную
```

`--drill` разворачивает копию **в отдельную базу** (`skyfraze_drill_<время>`), во
временный каталог распаковывает архив файлов, сверяет, что у **каждой** строки вложения
в базе есть файл в архиве, печатает сводку и убирает за собой. Рабочая база и рабочие
файлы не трогаются, поэтому проверку можно делать в любое время.

Сверяются **уникальные** файлы, а не строки: два вложения с одинаковым содержимым делят
один файл (дедупликация по `content_hash`), поэтому «вложений 22, файлов 4» — это норма,
а не пропажа. Именно на этом счётчик раньше врал: один отсутствующий файл, на который
ссылаются несколько строк, показывался как «у 18 вложений нет файлов».

Пример вывода:

```
=== копия backups/2026-10-02_033012 ===
проектов:     3
пользователей: 2
системных:    1 (аккаунт агента, не человек)
вложений:     4
файлов:       8
файлов нет у вложений: 0
проверка пройдена: копия восстанавливается, у всех вложений есть файлы
```

«Пользователей» — это люди: системный аккаунт агента «Нестор» (`users.is_system`,
миграция 0011) считается отдельной строкой и человеком не является.

Делать это стоит раз в квартал (или после каждой смены схемы) — иначе о неработающей
копии узнают в самый неподходящий момент.

## 5. Полное восстановление стенда

Восстановление **перезаписывает** базу и файлы, поэтому сначала убедитесь, что берёте
нужную копию, и сделайте копию текущего состояния (пусть даже сломанного — иногда это
единственный источник последних правок).

```bash
cd /home/skyadmin/skyfraze
bash deploy/backup.sh                        # копия текущего состояния «на всякий случай»

# 1. Остановить приложение: база и каталог должны быть не в работе.
docker compose -f docker-compose.prod.yml stop backend frontend

# 2. База: удалить и создать заново, затем восстановить.
docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -U skyfraze -d postgres -c 'DROP DATABASE IF EXISTS skyfraze;'
docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -U skyfraze -d postgres -c 'CREATE DATABASE skyfraze OWNER skyfraze;'
docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_restore -U skyfraze -d skyfraze --no-owner < backups/2026-10-02_033012/db.dump

# 3. Файлы вложений: очистить каталог и распаковать архив.
docker compose -f docker-compose.prod.yml run --rm --entrypoint sh backend \
  -c 'rm -rf /app/storage/*'
docker compose -f docker-compose.prod.yml exec -T backend \
  tar xzf - -C /app/storage < backups/2026-10-02_033012/assets.tar.gz

# 4. Поднять и проверить.
docker compose -f docker-compose.prod.yml up -d
curl -s http://127.0.0.1/api/health
```

После подъёма — глазами: открыть проект с картинками, проверить, что кадры и вложения на
месте. Отдельно полезно заглянуть в админку, раздел «Хранилище»: там видно сверку каталога
с базой (`пропавших файлов: 0` после восстановления должно быть именно так).

Если копия снималась со **старого** формата, сервер применит недостающие миграции при
старте — это нормально и предусмотрено (`platform.RunMigrations`).

## 6. Чего копии не заменяют

- **Историю правок внутри суток.** Копия фиксирует состояние на момент снятия; «верни как было час назад» решает история версий проекта (docs/versions.md), а не бэкап. Раньше у проекта был один снапшот CRDT, и это ограничение было абсолютным — с миграции 0016 оно снято.
- **Проверку того, что копия читается.** Файлы проверяются `sha256sum -c` и `--drill`, но
  целостность носителя — нет: копию на другом диске/машине никто не проверяет, пока её не
  восстанавливают.
- **Защиту от «удалил и не заметил».** Сутки между копиями — это сутки потерянных правок.
  Если это критично, копии можно снимать чаще (`systemd`-таймер или `BACKUP_KEEP` больше),
  но принцип тот же: копия — снимок, а не журнал.
- **Секреты из `.env`.** Копия содержит базу и файлы, а `.env` (в нём `JWT_SECRET` и
  `AI_SECRET_KEY`, которым зашифрованы пользовательские ключи провайдеров) — нет: это
  настройка стенда, а не данные. Восстановление на другую машину без того же `.env`
  означает: сессии перестанут приниматься, а ключи ИИ-помощника не расшифруются — сервер
  скажет «ключ провайдера не читается — введите его заново», и человеку придётся вставить
  ключ ещё раз (`docs/ai-assistant.md`). Сам `.env` храните отдельно от копий, но так же
  бережно: без него копия не даёт полностью рабочего стенда.
