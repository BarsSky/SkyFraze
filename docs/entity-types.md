# Свои типы карточек и перенос шаблонов между проектами

Разбор просьбы: «сделать свободное создание типов карточек и выбирать из уже созданных —
Персонаж, Место, Тема оставить вариантами по умолчанию, но добавить возможность в проекте
формировать свои; а также чтобы шаблоны и настройки можно было переносить между проектами».

Документ-план: что решаем, что меняется в данных, что видит человек, что переносится и чего
сознательно не делаем. Кода здесь нет — есть решения, которые иначе пришлось бы принимать по ходу.

## 1. Что есть сейчас и почему «вид» — это три константы

Вид карточки (`kind`) — не свободный текст, а `character | place | theme`:

* `backend/internal/store/store_entity.go` — `ParseEntityKind` и CHECK в миграции `0030`:
  `kind IN ('character','place','theme')`;
* `frontend/src/api/entities.ts` — `EntityKind` и `kindLabel` (Персонаж / Место / Тема);
* анализ упоминаний и матрица вид не используют вовсе (они про имя и алиасы), поэтому
  расширение вида **не ломает** поиск упоминаний, хронологию, граф и матрицу;
* помощник перечисляет вид в описании инструмента `propose_entities` (`enum`).

Отсюда главный вывод: вид — это **классификация для человека** (подпись и цвет в списке), а не
механизм связей. Значит расширять его безопасно, если сохранить три прежних значения.

## 2. Решение: типы живут в проекте, «вид» становится ссылкой на тип

### 2.1. Данные

Новая таблица `project_entity_types` (миграция `0034`):

| колонка | смысл |
|---|---|
| `id` | идентификатор типа |
| `project_id` | тип принадлежит проекту (как и карточки) |
| `key` | машинное имя для API и экспорта: `character`, `place`, `theme`, `faction`, … (уникально в проекте, `lower(key)`) |
| `title` | как называть человеку: «Персонаж», «Фракция» (1–40 знаков) |
| `icon` | один символ или shortcode для списка (`⚔`, `🏰`) — необязательно |
| `color` | тот же `#rrggbb`, что у карточки: тип задаёт цвет по умолчанию |
| `position` | порядок в выпадающем списке |
| `is_default` | `true` у трёх стартовых: их нельзя удалить, только переименовать |

В `project_entities` поле `kind` **не удаляем и не переименовываем**: в нём остаётся `key` типа
(`text` с FK на `project_entity_types(project_id, key)` и `ON UPDATE CASCADE`). Почему так, а не
`type_id`:

* старые архивы, старые сборки и уже написанные тесты продолжают работать без переделки;
* `kind` уже приходит в API карточек — менять контракт ради красоты значит ломать клиентов;
* CHECK на три значения снимается (миграция `0034`), вместо него — FK: вид карточки обязан
  существовать в проекте.

Стартовые типы создаются **при создании проекта** (три строки) и досоздаются миграцией для уже
существующих проектов (`INSERT ... SELECT` по проектам). Не «глобальные» типы в отдельной
таблице: человек, заведя «Фракцию» в одном проекте, удивится, увидев её в чужом.

### 2.2. API

```
GET    /api/projects/{id}/entity-types            → [{id, key, title, icon, color, position, is_default}]
POST   /api/projects/{id}/entity-types            → создать (editor+)
PATCH  /api/projects/{id}/entity-types/{tid}      → переименовать, сменить цвет/значок
DELETE /api/projects/{id}/entity-types/{tid}      → удалить (только НЕ default)
```

Правила отказа (текстом, а не кодом):

* удаление типа, у которого есть карточки, — `409` со списком: «в типе «Фракция» 4 карточки:
  сначала переведите их в другой тип»; каскадом не удаляем — это тихая потеря классификации;
* `key` неизменяем после создания (на него ссылаются карточки, экспорт и помощник); переименование
  — только `title`;
* ключ из трёх стартовых зарезервирован: `character/place/theme` нельзя создать заново или
  удалить;
* лимит типов на проект — 24: дальше это уже не классификация, а свалка.

Карточки: `GET/POST /entities` принимает `kind` = `key` любого типа проекта. Ответ карточки
дополнительно отдаёт `kind_title` и `kind_color` — чтобы списки не тянули вторую ручку.
`kindLabel` на клиенте перестаёт быть константой: подпись берётся из типов проекта, а
неизвестный ключ показывается как есть (не «Персонаж» по умолчанию — это ложь о данных).

### 2.3. Что видит человек

* В панели «Связи проекта» форма создания: выпадающий список типов, а рядом кнопка
  **«+ новый тип карточки»** (не в настройках проекта: тип придумывают в момент, когда заводят
  карточку). С 0.111.0 она открывает **всплывающее окно** — название, алиасы и заготовка описания.
  До этого три поля достраивались прямо под формой карточки, сдвигали список и читались как её
  продолжение: человек вводил имя персонажа в «название типа». Закрывается Escape, кликом мимо и
  «Отменой», фокус возвращается в список видов;
* переименование типа — в том же списке (долгое нажатие/карандаш), удаление — там же, с отказом
  при наличии карточек;
* цвет и значок типа — по умолчанию у новых карточек; у отдельной карточки цвет по-прежнему
  можно переопределить (поле `color` уже есть);
* помощник: `propose_entities` получает **актуальный список типов проекта** в описании
  инструмента (`enum` собирается по проекту — инструменты строятся на каждый запрос, это уже
  так), поэтому он не придумает «фракцию», которой нет.

### 2.4. Что едет в архиве

`project_entity_types` попадают в `manifest.json` (поле `entity_types`) рядом с карточками.
Импорт: сначала типы, потом карточки — иначе первая же карточка с новым `kind` нарушит FK.
Неизвестный тип в чужом архиве создаётся с `is_default: false`; занятый `key` с другим
`title` — конфликт, который показывается строкой отчёта (как «карточка уже есть»), а не молча
переименовывается.

## 3. Перенос шаблонов и настроек между проектами

«Шаблон» здесь — не текст, а **устройство проекта**: из чего он состоит и как себя ведёт.
Переносим ровно то, что человек настраивал руками и что не является содержимым:

| Что | Почему переносим |
|---|---|
| типы карточек (ключ, название, цвет, значок) | иначе в новом проекте снова заводить классификацию |
| карточки-заготовки (имя, алиасы, описание) — по выбору, галочкой | «в этой серии те же герои» |
| роль и указания ИИ-помощника, режим генерации, стиль иллюстраций | это и есть «привычки», которые жалко терять |
| негативный промпт и шаги генерации (если заданы на проект) | часть стиля |
| настройки уведомлений проекта | редко меняются, но переносятся дёшево |

**Не переносим:** кадры и их текст (это содержимое, для этого есть архив), участников и права
(это люди, а не настройки), оценки/просмотры/публикацию (это факты о проекте), историю версий.

Как это работает:

1. **Внутри инсталляции** — `GET /api/projects/{id}/template` отдаёт JSON
   `{version: 1, entity_types: [...], cards: [...], ai: {...}, notify: {...}}`;
   `POST /api/projects/{id}/template` применяет его к проекту (editor+, с отчётом:
   «добавлено 3 типа, 2 карточки уже были, роль помощника обновлена»).
2. **Между инсталляциями** — тот же JSON: скачать файлом и загрузить. Архив проекта тоже
   содержит `template.json` — так «начни новый проект по образцу старого» делается из уже
   существующего экспорта, без отдельной сущности.
3. **При создании проекта** — выбор «с нуля» или «по шаблону» (из файла или из проекта-образца).
   Здесь же пригодится `is_default` у типов: «с нуля» = три стартовых типа.

Правила применения, чтобы перенос не был лотереей:

* **слияние, а не замена**: существующие типы с тем же `key` обновляются по `title/color/icon`,
  остальные добавляются; карточки с занятым именем пропускаются и попадают в отчёт;
* **права**: применять шаблон может только владелец — это меняет настройки проекта целиком;
* **отчёт идемпотентность**: повторное применение того же шаблона ничего не меняет и говорит
  «всё уже на месте» (проверяется тестом);
* **ничего не удаляется**: шаблон не умеет убирать типы, карточки или настройки. Удаление — только
  руками: «применил шаблон, и часть настроек исчезла» — это уже не перенос, а тихая потеря.

## 4. Шаблоны карточек — отдельно от типов

Просьба про шаблоны может означать и заготовки **одной карточки**: «Порт: имя, алиасы, описание
— вот пустая заготовка, чтобы не писать одно и то же». Это дешевле и полезнее, чем кажется:
тип даёт `title/color`, а шаблон — предзаполненные поля.

Решение: в `project_entity_types` добавляем `card_template jsonb` (`description` с
`{{name}}`-подстановками, набор типичных алиасов). При создании карточки выбранный тип
подставляет этот текст, человек его правит. Это одна колонка и одно поле в форме — без новой
сущности «шаблон карточки».

## 5. Порядок работ

| Фаза | Что | Оценка | Состояние |
|---|---|---|---|
| 1 | миграция `0034`: `project_entity_types`, FK и снятие CHECK, досоздание трёх типов существующим проектам; store + сервис + ручки типов; тесты правил отказа | 3–4 ч | сделано (0.81.0) |
| 2 | панель: список типов, «+ новый тип», переименование, удаление с отказом; `kindLabel` из типов; тесты | 3 ч | сделано (0.81.0) |
| 3 | помощник: `enum` типов в `propose_entities`, проверка `kind` по типам проекта | 1–2 ч | сделано (0.81.0) |
| 4 | шаблон проекта: `GET/POST .../template`, отчёт, идемпотентность, `template.json` в архиве, «создать по шаблону» | 3–4 ч | сделано (0.85.0) |
| 5 | `card_template` у типа + подстановка в форме | 1–2 ч | сделано (0.85.0) |

Итого **11–15 часов**, 3–4 сессии. Фазы 1–3 дают «свои типы», 4 — «переносить между проектами»,
5 — заготовки карточек.

### 5.1. Как это сделано в 0.85.0 (что именно появилось)

**API.** `GET /api/projects/{id}/template` (editor+; `?cards=0` — без карточек) отдаёт
`{version, entity_types[], cards[], ai{role,instructions,enabled,generation,image_style}}`;
`POST /api/projects/{id}/template` (только владелец) применяет шаблон и возвращает отчёт
`{types_added, types_updated, types_skipped[], cards_added, cards_skipped[], ai_updated, changed,
message}`; `POST /api/projects/from-template` создаёт проект сразу по образцу (одна ручка, а не два
запроса: иначе неудачное применение оставляло бы пустой проект).

**Правила применения — те же, что в §3**: слияние, а не замена; карточки по имени (занятое —
пропуск с причиной); ничего не удаляется; повторное применение даёт `changed: 0` и
«всё уже на месте». `changed` — единственное число, по которому интерфейс отличает «перенос
сработал» от «переносить нечего».

**Архив.** `template.json` лежит в экспорте отдельным файлом (не полем манифеста: тот же JSON
отдаёт `GET /template`, и два парсера одного формата — лишний риск). Импорт применяет шаблон
ДО карточек (иначе первая карточка своего типа нарушила бы внешний ключ) и не валит импорт из-за
настроек: битый `template.json` игнорируется, содержимое проекта важнее. Старые архивы читаются —
файла просто нет.

**Заготовка карточки (`card_template`, миграция `0035`).** У типа есть `{description, aliases[]}`;
`{{name}}` подставляется при вводе имени. Заготовка подставляется в форму карточки и правится
человеком: после первой правки руками подстановка это поле больше не трогает
(`descriptionEdited`/`aliasesEdited`). Заодно у карточки появилось поле описания в интерфейсе —
раньше его можно было только прочитать, если оно приехало из импорта или от помощника.

**Заготовка применяется на СЕРВЕРЕ (0.92.2).** До 0.92.2 заготовку знала только форма: карточка,
созданная помощником (`propose_entities`) или через API, оставалась без описания и алиасов типа —
тип «Порт» с описанием «{{name}} — порт…» давал человеку одно, а помощнику другое. Теперь правило
одно и живёт в `entities.Service.Create`: **заготовка заполняет только пустые поля**, присланное
значение (человек, помощник, импорт) всегда сильнее; `{{name}}` подставляется; алиасы заготовки
проходят те же проверки, что и введённые руками, а негодный алиас отбрасывается, а не валит
создание карточки. Правило и семантика — `applyCardTemplate` в `backend/internal/entities/service.go`,
тест — `entity_template_integration_test.go`.

**Чего в шаблоне нет и почему.** Настроек уведомлений проекта в приложении пока не существует
(уведомления — очередь писем о замечаниях на уровне установки), негативный промпт и шаги
генерации живут в конфигурации стенда, а не проекта: переносить пустые поля значило бы обещать
то, чего нет.

## 6. Чего сознательно не делаем

* **Глобальных типов на всю инсталляцию** — это те же «сущности между проектами», которые уже
  отклонены в `docs/entity-links.md` (§4): отдельный контур прав и миграции. Шаблон решает задачу
  «перенести в новый проект» без глобального состояния.
* **Свободного текста вместо типа** (`kind: "что угодно"`): тогда фильтры, матрица и отчёты
  начнут группировать «Фракции» и «фракции» отдельно. Тип — строка в таблице, потому что по нему
  группируют.
* **Удаления типа каскадом с карточками** — тихая потеря данных.
* **Переноса содержимого шаблоном** — для содержимого есть архив и импорт Markdown.
* **Своих полей у типа** (произвольные атрибуты карточки): это уже «конструктор сущностей», он
  меняет и API, и матрицу, и помощника. Сначала пусть проверятся типы и шаблоны.

## 7. Риски

| Риск | Как проверяем |
|---|---|
| Снятие CHECK ломает старые карточки | миграция создаёт типы до FK; тест: проект из 0.77 поднимается без потерь |
| Помощник предлагает несуществующий тип | `enum` строится по проекту; тест «предложение с чужим типом отвергается до подтверждения» |
| Шаблон затирает настройки | слияние без удаления + отчёт + тест идемпотентности |
| Перенос архива с новым типом падает на FK | импорт типов раньше карточек; тест «экспорт → импорт в чистую базу» |
| Подпись типа разъезжается с `key` | `key` неизменяем; тест «переименование меняет `title`, но не `key`» |
